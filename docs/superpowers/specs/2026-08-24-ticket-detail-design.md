# 티켓 상세·제목 수정·댓글 등록 설계

카드를 누르면 티켓의 본문과 댓글을 읽고, 제목을 고치고, 댓글을 달 수 있게 한다. 앱을 떠나지 않고 할 수 있는 일을 늘리는 것이 목적이다.

이 문서는 계획 2b-2의 **1차**를 다룬다. 본문 편집과 댓글 수정은 2차로 미뤘고 그 이유는 §10에 적었다.

## 1. 왜 이 범위인가

Jira Cloud REST API v3에서 본문(`description`)과 댓글(`body`)은 **ADF**(Atlassian Document Format)라는 JSON 트리다. 평문이 아니다. 네 가지 쓰기 동작의 왕복 손실 위험이 고르지 않다.

| 동작 | 형식 | 왕복 손실 |
|---|---|---|
| 제목 수정 | 평문 문자열 | 없음 |
| 새 댓글 등록 | ADF (우리가 처음부터 작성) | 없음 |
| 댓글 수정 | ADF (남이 쓴 리치 댓글일 수 있음) | 가능 |
| 본문 수정 | ADF (표·코드블록·패널 포함 가능) | 큼 |

1차는 **왕복 손실이 0인 것까지**만 만든다. 남의 티켓 본문에 있던 표나 코드블록을 평문으로 왕복시키면 되돌릴 수 없이 부순다.

## 2. 채점을 건드리지 않는다는 것의 의미

이 앱의 핵심 불변은 "채점이 관측된 이벤트 로그의 순수 함수"이고, 앱이 자기가 한 일로 점수를 벌 수 없어야 한다.

### 2.1 `.touched`의 wake XP를 없앤다

지금 `XpAwarder`는 `.touched`(상태는 그대로인데 `jiraUpdatedAt`이 움직임)에 **깨우기 XP**를 준다. 정체가 길수록 크고 최대 160점이다. 실행자 필터(`awardsOnlyOwnTransitions`)는 **남의 작업을 0점 처리하는** 방향이라, 내가 앱에서 단 댓글은 오히려 통과한다.

댓글 상자를 다는 순간 이것은 **한 번 클릭으로 XP를 얻는 버튼**이 된다. `AbuseGuard`의 중복 창은 같은 티켓의 반복만 막으므로, 티켓 49건에 각각 댓글을 달면 일일 상한까지 긁어모을 수 있다.

실제 이벤트 로그를 세어 보면 이 규칙은 사실상 쓰이지 않는다.

| 종류 | 개수 |
|---|---|
| `statusChanged` | 5,894 |
| `appeared` | 49 |
| `touched` | **1** |

백필이 Jira 변경이력에서 만드는 이벤트는 전부 `statusChanged`이고, `.touched`는 동기화 사이에 상태 없이 `jiraUpdatedAt`만 움직일 때만 생긴다. **쓰이지 않으면서 게임 여지만 열어두고 있었다.**

`XpAwarder`의 `case .touched:`가 `wakeXP(...)` 대신 0을 돌려준다. `wakeXP` 함수 자체는 남는다 — `transitionXP`가 내부에서 쓴다.

### 2.2 연속 기록까지 움직인다

`ScoreEngine.checkInDays`는 **XP가 붙은 이벤트가 하루에 한 건이라도 있으면 그날을 체크인으로 센다**. 그날의 유일한 XP가 touched였다면 그날이 체크인에서 빠지고, 연속 기록이 끊기면 **이후 모든 날의 배수**가 달라진다.

실측상 touched가 1건이라 파급은 작지만, "재집계가 순수 함수라 자동 반영된다"로 넘길 일이 아니다. 재집계 회귀 테스트로 고정한다.

### 2.3 순서 제약 — 규칙 변경이 먼저다

댓글 등록 기능이 `wakeXP`가 살아 있는 채로 출하되면, 앱이 스스로 파밍 가능한 이벤트를 찍는다. **§2.1의 규칙 변경이 댓글 쓰기보다 먼저 나가야 한다.** 구현 계획의 태스크 순서로 강제한다.

## 3. 데이터가 어디까지 들어오는가

**본문과 댓글은 미러(`IssueSnapshot`)에 넣지 않는다.**

넣으면 세 가지가 따라온다. SwiftData 마이그레이션, 용량(티켓 수 × 본문 + 댓글), 그리고 `DiffEngine` 오염이다. 본문이 미러에 있으면 "본문이 바뀌었다"가 이벤트가 될 수 있는데 그것은 채점 입력이 아니다.

```
카드 클릭 → 시트 열림
          → GET /issue/{key}?fields=summary,description
          → GET /issue/{key}/comment?orderBy=-created&maxResults=20
          → 화면 상태로만 보관 (미러 미접촉)
시트 닫힘 → 버린다. 다시 열면 다시 받는다.
```

미러는 채점 입력만 담는다는 기존 원칙을 그대로 지킨다.

### 3.1 각주 — 표시 정체일은 영향을 받는다

점수는 안전하지만 화면은 완전히 무관하지 않다.

`BoardLayout`은 관측된 상태 변화가 없는 티켓의 정체일을 `jiraUpdatedAt` 폴백으로 계산한다. 그런 티켓에 앱에서 댓글을 달면 **화면의 정체일이 0으로 리셋된다.** 이 앱이 재려는 값 그 자체다.

Jira 웹에서 댓글을 달아도 같고, 그런 티켓에는 이미 추정 표시(`baselineIsFallback`)가 뜬다. 그래도 댓글 버튼을 다는 설계가 이 사실을 적지 않을 수는 없다. 1차에서는 동작을 바꾸지 않고 사실만 기록한다.

## 4. ADF를 화면에 옮긴다

1차에는 **렌더러만** 필요하다. 편집 가능 판정은 본문 편집과 함께 2차로 간다.

세 모듈이 각자 하나씩 맡는다.

| 모듈 | 책임 |
|---|---|
| `JiraKit` | ADF JSON → `ADFNode` 트리. 파싱만. |
| `ArcadeCore` | `ADFRenderer.plainText(from:)` — 화면에 그릴 문자열 |
| `ArcadeUI` | 결과를 그린다. **판단 없음** |

`ArcadeUI`에는 테스트 타깃이 없다. 판단이 뷰에 들어가면 어떤 테스트도 닿지 못한다.

### 4.1 모든 노드가 무언가로 그려져야 한다

이것이 렌더러의 어려운 절반이다. 실제 Jira 본문과 댓글에는 문단만 있지 않다.

| 노드 | 1차 처리 |
|---|---|
| `doc`, `paragraph`, `text`, `hardBreak` | 그대로 |
| `bulletList`, `orderedList`, `listItem` | `• ` / `1. ` 접두어 |
| `codeBlock` | 들여쓴 블록 |
| `blockquote` | `> ` 접두어 |
| `heading` | 굵은 한 줄 |
| `rule` | 구분선 |
| `mention` | `@이름` (`attrs.text`) |
| `emoji` | `attrs.text`가 있으면 그것, 없으면 `attrs.shortName` |
| `inlineCard` | 링크 URL (붙여넣은 URL이 이 노드가 된다) |
| `mediaSingle`, `mediaGroup`, `media` | `[첨부]` 자리표시자 |
| `table` 계열 | `[표]` 자리표시자 |
| **그 밖의 모든 노드** | `[지원하지 않는 서식]` 자리표시자 |

**미지의 노드를 조용히 빠뜨리지 않는다.** 빠뜨리면 본문 일부가 없는 채로 보이고 사용자는 그게 전부인 줄 안다. 자리표시자가 있으면 "여기 뭔가 더 있다"가 보이고, 시트의 `Jira에서 열기`로 갈 수 있다.

`marks`(굵게·기울임·링크)는 1차 렌더에서 무시한다 — 평문으로 그리므로 텍스트만 남는다. 텍스트가 사라지지는 않는다.

## 5. 쓰기 경로

### 5.1 무엇을 쓰는가

- **제목**: `PUT /issue/{key}` 본문 `{"fields":{"summary":"..."}}`
- **새 댓글**: `POST /issue/{key}/comment` 본문은 ADF. **우리가 처음부터 만든다** — 왕복이 없으므로 손실도 없다.

입력 문자열에서 ADF를 만드는 규칙을 못박는다. 이 규칙이 애매하면 같은 입력이 두 가지 결과를 낸다.

- 빈 줄(연속된 줄바꿈 둘 이상)이 **문단 경계**다. 문단 사이의 빈 줄이 몇 개든 경계 하나로 본다.
- 문단 안의 줄바꿈 하나는 `hardBreak` 노드다.
- 앞뒤 공백은 잘라내고, 결과가 비면 저장하지 않는다.

### 5.2 충돌은 감지하지 않는다 — 마지막 쓰기가 이긴다

Jira Cloud의 `PUT /issue`와 `POST /comment`에는 낙관적 잠금이 없다. 409도 412도 오지 않는다. 저장 직전에 `updated`를 다시 읽어 대조하는 방법이 있으나, GET과 PUT 사이의 틈은 여전히 남고 요청이 하나 는다.

Jira 웹의 기본 동작과 같게 둔다. 시트를 열어둔 채 자리를 비운 사이 남이 제목을 고쳤다면 저장이 그걸 되돌린다 — 이 한계를 문서에 남긴다.

### 5.3 취소 창은 없지만 생명주기는 그대로다

전이 쓰기에는 5초 취소 창이 있다. 텍스트 편집에는 두지 않는다 — 전이는 한 번 클릭이라 오조작이 쉽지만, 텍스트는 입력과 저장 버튼에 이미 숙고가 들어 있다.

**취소 창을 빼는 것과 대기 상태를 안 만드는 것은 다르다.** `AppModel`의 전이 상태는 취소 버튼만을 위한 것이 아니라 **진행 중인 비동기 작업의 수명을 계정 경계에 묶는 장치**다. 취소 창이 없어도 저장은 `await`이고, 그 사이에 계정이 바뀔 수 있다.

그러므로 다음이 전부 필요하다.

- **티켓별 진행 중 상태**를 만들고 `signOut()`이 지운다. 진행 중 작업은 취소한다.
- 결과 상태를 쓰거나 `syncNow()`를 부르기 **전에 `syncGeneration`을 확인한다.** 세대가 다르면 조용히 버린다.
- **401은 `.expired`로 옮긴다** — `executeTransition`과 같은 처리.
- **저장 중에는 버튼을 잠근다.** 댓글 `POST`는 멱등이 아니라 이중 제출이 댓글을 둘로 만든다.
- 쓰기 대상이 현재 미러에 있는 티켓인지 확인한다 — `requestTransition`이 하는 것과 같다.

이 목록이 없으면 지난 사이클에 출하됐던 버그가 그대로 재현된다. 그때는 로그아웃 후 대기 중이던 전이가 **다음 계정의 사이트로** 발사됐다.

### 5.4 쓰기 뒤에는 동기화한다

성공하면 `syncNow()`를 부른다. 전이와 같다. 앱이 XP를 직접 주지 않고 **관측을 통해서만** 점수가 움직인다는 불변을 지키기 위해서다.

제목 수정은 미러의 `summary`를 갱신해야 카드의 제목이 맞는다. `DiffEngine`은 `summary`를 비교하지 않으므로 이벤트는 생기지 않는다.

## 6. 실패 처리

**Jira 응답 본문 조각이 화면에 닿지 않는다.** 이 제약이 새 경로에서 특히 위험하다.

`JiraClient.mapError`는 **400을 `.transitionRejected(reason:)`로 감싸고 그 `reason`은 Jira 응답 본문**이다. 제목이 너무 길거나 댓글이 거부되면 정확히 이 경로를 탄다. 기존 전이 경로는 `AppModel.transitionFailureMessage`가 앱이 직접 쓴 문구로 갈아끼우지만, 새 경로는 그 처리를 공짜로 얻지 못한다.

- 쓰기 실패 문구는 **앱이 쓴다.** 사유가 필요하면 `Jira에서 열기`로 보낸다.
- 시트의 조회 실패도 마찬가지다. 시트 조회는 `performSync`의 `SyncFailure` 축약 밖에서 돌므로 기존 `redactedErrorDescription`을 **명시적으로** 거쳐야 한다.
- 실패 표시는 시트 안에 **티켓별 편집 실패 상태**로 둔다. 카드의 전이 실패 블록을 그대로 쓰지 않는다 — 문구가 "전이"를 말하고, 시트를 닫아도 살아남는다.

## 7. 댓글 로딩

`GET /issue/{key}/comment`의 기본 정렬은 **오래된 순**이다. `orderBy=-created`를 명시해 최신순으로 받고 20건만 가져온다. 나머지는 `Jira에서 열기`로 보낸다.

페이지네이션은 만들지 않는다. 이 앱은 티켓을 읽는 도구가 아니라 정체를 재는 도구이고, 최근 대화만 있으면 "지금 무슨 상황인가"는 판단할 수 있다.

## 8. 화면

카드에서 **시트**로 연다. 퀘스트 보드가 맥락이고 시트를 닫으면 그 자리로 돌아온다. `Cabinet`의 `CabinetPresentation.sheet`가 이미 기본값이다.

시트 안에서 상세를 받아오는 판단은 **`AppModel`의 API**여야 한다(`loadIssueDetail(key:)` 같은 형태). 조회·실패·저장 상태 기계를 뷰가 소유하면 `ArcadeUI`에 테스트 타깃이 없으므로 구조적으로 검증 불가능해진다.

## 9. 새로 필요한 `JiraKit` 표면

현재 쓰기는 `performTransition` 하나뿐이다. 다음이 전부 새로 생긴다.

- 상세 조회 DTO (`summary`, `description`)
- 댓글 페이지 DTO
- `ADFNode` 파서
- `PUT /issue/{key}` — 제목
- `POST /issue/{key}/comment` — 새 댓글
- 새 오류 경로의 축약 처리

## 10. 테스트 전략

| 계층 | 무엇을 덮나 |
|---|---|
| `ArcadeCore` | ADF 파싱, `plainText` 노드별 렌더, **미지 노드가 자리표시자로 나오는지**, 입력 문자열 → ADF 문단 배열 |
| `ArcadeApp` | 쓰기 성공·실패, `signOut()`이 편집 상태를 지우는지, 세대 검사, 401 → `.expired`, 이중 제출 잠금, `syncNow` 호출 |
| `ArcadeCore` (회귀) | `.touched` 0점화 후 재집계 — XP와 **연속 기록** 둘 다 |
| `ArcadeUI` | 테스트 타깃 없음. 판단이 여기 들어가면 안 된다 |

테스트는 Swift Testing(`@Test` / `#expect`)을 쓴다. 조직 특정 정보를 넣지 않는다 — `example.atlassian.net`과 `DEMO-`만 쓴다.

## 11. 완성 정의

- [ ] 카드를 누르면 시트가 열리고 본문과 최근 댓글 20건이 보인다
- [ ] 본문에 표·첨부·미지의 서식이 있어도 자리표시자로 표시되고 내용이 조용히 사라지지 않는다
- [ ] 제목을 고쳐 저장하면 Jira에 반영되고 카드의 제목이 따라 바뀐다
- [ ] 댓글을 달면 Jira에 등록되고 시트에 나타난다
- [ ] 저장 중에는 버튼이 잠겨 이중 제출이 되지 않는다
- [ ] 저장 실패 문구에 Jira 응답 본문이 들어가지 않는다
- [ ] 저장 도중 로그아웃해도 다음 계정에 아무것도 쓰지 않는다
- [ ] `.touched`가 XP를 주지 않는다 — 재집계 후 XP와 연속 기록이 테스트로 고정된다
- [ ] 채점 규칙 변경이 댓글 기능보다 먼저 들어간다
- [ ] 전체 테스트가 통과한다

## 12. 2차로 미룬 것

- **본문 편집.** 편집 가능 판정(`editability(of:)`)이 필요하다. 손실 없이 평문으로 표현되는 ADF만 편집을 열고, 나머지는 읽기 전용으로 잠근다. 판정은 **화이트리스트**여야 한다 — `doc`·`paragraph`·`text`·`hardBreak`만 허용하고 `marks` 없는 `text`만 통과. 블랙리스트로 만들면 Atlassian이 새 노드 타입을 추가할 때 조용히 통과시켜 그 내용을 파괴한다.
- **`marks`를 허용하지 않는 이유.** 굵게나 링크를 "허용"한다는 것은 평문 편집기가 저장할 때 그것을 **조용히 지운다**는 뜻이다. 화이트리스트가 막으려던 파괴 그 자체다. 링크가 있는 본문이 대부분 읽기 전용이 되는 대가를 치르더라도, 부수는 것보다 거절하는 쪽이 맞다. 읽기 전용 비율이 문제가 되면 답은 게이트를 느슨하게 하는 것이 아니라 더 나은 편집기다.
- **댓글 수정.** 우리가 쓴 댓글이면 안전하지만 남이 쓴 리치 댓글이면 같은 왕복 문제가 있다. 본문 편집과 같은 판정을 공유한다.

## 13. 남은 위험과 후속

- **표시 정체일 리셋**(§3.1). 1차는 사실만 기록한다. 폴백 기준선 티켓에 한정된 문제이고, 근본 해결은 이슈 #6(왕복 시 기준선 유지)과 같은 계열이다.
- **마지막 쓰기가 이긴다**(§5.2). 동시 편집이 잦아지면 저장 직전 `updated` 대조를 다시 검토한다.
- **댓글 20건 상한**. 더 필요하다는 신호가 오면 페이지네이션을 검토한다.
- 이슈 #9(툴팁 육안 검증), #10(이름 없는 스프린트 원소), #11(설계문서의 조직 식별자)은 이 계획과 독립이다.
