# 스프린트 이월 표시 설계 (계획 2b-3)

- 작성일: 2026-08-24
- 상태: 확정 (구현 계획 작성 대기)
- 선행: `docs/superpowers/specs/2026-08-12-jirarcade-design.md` (v0.1 전체 설계)

## 1. 배경 — 계획이 조사 결과로 바뀌었다

이 계획은 원래 **스프린트 보드**였다. v0.1 스펙 §10이 "스프린트·보드 (Agile API) — 엔드포인트
체계가 별개"라며 제외했고, 퀘스트 보드 스펙도 `AuthProvider.baseURL`이 `/rest/api/3`에
묶여 있어 계약 변경이 선행한다고 적었다.

실제 Jira를 조사하니 전제 셋이 무너졌다.

**① Agile API가 필요 없다.** 스프린트 정보는 이미 `/search/jql` 응답에 온다. 커스텀 필드로
배열이 오고 각 원소가 `{id, name, state, boardId, goal, startDate, endDate, completeDate}`를
담는다. `AuthProvider` 계약 변경도, `/rest/agile/1.0` 클라이언트도 불필요하다.

**② 활성 스프린트가 없다.** `project = MPT AND sprint in openSprints()`가 0건이다.
내 티켓 50건의 스프린트 상태 분포는 `closed` 236 · `future` 26 · `active` 0이었다.
"현재 스프린트를 보여준다"는 화면은 지금 이 조직에서 성립하지 않는다.

**③ 티켓이 여러 스프린트에 걸쳐 있다.** 스프린트 필드는 배열이고, 실측에서 한 티켓이
13개 스프린트에 속해 있었다(MPT-9141: 52번 3월 19일 → 66번 8월 6일, 약 5개월).

③이 이 앱과 정확히 맞물린다. README 첫 문단은 이 앱이 "이 티켓이 며칠째 멈춰 있었는가"를
재려고 만들어졌다고 말한다. **이월 횟수는 그 스프린트 버전이다** — "며칠 멈췄나"가 아니라
"몇 번이나 다음으로 미뤄졌나"이고, 스프린트 계획 회의에서 실제로 쓰이는 단위다.

그래서 이 계획은 스프린트 보드를 만들지 않는다. **기존 퀘스트 보드의 카드에 이월 횟수를
더한다.**

### 1.1 이 값이 특별한 이유

이 앱이 아는 역사는 관측을 시작한 날부터다. 그래서 정체일에 근사 표시(`~`)가 붙는다 —
관측 이력이 없는 티켓은 `jiraUpdatedAt`으로 추정할 수밖에 없다.

**스프린트 이력은 다르다.** Jira가 티켓 생성 시점부터 완전하게 들고 있고, 매 동기화 응답에
전부 실려 온다. 이 앱이 다루는 지표 중 **유일하게 과거가 온전한 값**이다. 근사 표시가 필요 없다.

## 2. 무엇을 만드는가

퀘스트 보드의 티켓 카드에 이월 횟수를 한 줄 더한다. 툴팁에 첫·마지막 스프린트 이름을 적는다.

```
┌──────────────────────┐
│ BOSS  41d            │
│ MPT-9141             │
│ [환자] 실시간 기상…    │
│ ↻ 스프린트 12회        │   ← 새로 더하는 줄
│ 상태 옮기기            │
└──────────────────────┘

툴팁: 모비닥 스프린트 (52) → 모비닥 스프린트 (66)
```

**채점에는 반영하지 않는다.** 보스전이 이미 정체일로 같은 일을 하고 있고, 규칙을 늘리면
두 지표가 같은 티켓에 중복으로 배수를 걸 수 있다. 표시가 유용한지 며칠 써 본 뒤에
채점 반영을 따로 판단한다(§10).

---

## 3. 스프린트 필드를 찾는 방법

**필드 ID는 사이트마다 다르고, 이름은 로케일에 따라 다르다.** 실측한 사이트에서
`names.customfield_10020`은 `"Sprint"`가 아니라 **`"스프린트"`** 였다. 이름으로 찾는 코드는
영어 사이트에서만 동작하고 한국어 사이트에서는 조용히 아무것도 찾지 못한다.

안정적인 식별자는 필드 스키마다:

```
schema.custom == "com.pyxis.greenhopper.jira:gh-sprint"
```

Atlassian이 Greenhopper 시절부터 유지해온 값이며 로케일과 무관하다.

**조회 시점:** 로그인 직후 `/rest/api/3/field`를 한 번 부른다. 이미 있는 `/status` 카탈로그
조회와 같은 성격이고 같은 API 버전이므로 `JiraClient`에 메서드 하나가 는다.

**저장:** 앱 지원 디렉터리에 **별도 JSON 파일**로 둔다. 계정이 바뀌면 함께 버린다 —
다른 테넌트의 필드 ID는 무의미하다.

`WorkflowStore`에 얹지 않는 이유: 그 프로토콜은 이미 사용자 매핑과 백필 폴백을 함께 떠안고
있고, history-backfill 후속 항목 §5.9가 "구현이 늘면 별도 프로토콜로 쪼개는 편이 낫다"고
지적해 두었다. 세 번째 관심사를 더하면 그 지적이 현실이 된다. 스프린트 필드 ID는 워크플로와
아무 관계가 없으므로 처음부터 따로 둔다.

**못 찾았을 때:** 이월 표시를 끄고 나머지는 그대로 돈다. 스프린트를 쓰지 않는 조직도 있고,
필드가 없다는 것은 오류가 아니라 사실이다. 화면에 경고를 띄우지 않는다.

## 4. 데이터 모델

`JiraKit`이 스프린트 원소를 값 타입으로 옮긴다:

```swift
public struct JiraSprint: Sendable, Equatable, Decodable {
    public let id: Int
    public let name: String
    /// `closed` / `future` / `active`. 이 계획은 구분하지 않지만(§5) 나중에 필요할 값이라 담는다.
    public let state: String
    /// 정렬 키. 드물게 없을 수 있다(§5).
    public let startDate: Date?
}
```

`goal`·`boardId`·`endDate`·`completeDate`는 담지 않는다 — 실측에서 `goal`은 전부 빈
문자열이었고 나머지는 이 계획이 쓰지 않는다(§9).

`ObservedIssue`와 `IssueSnapshot`에 세 값을 더한다.

```swift
/// 이 티켓이 거쳐 온 스프린트 수 - 1. 스프린트가 없거나 하나뿐이면 0이다.
public let sprintCarryOvers: Int
/// 가장 이른 스프린트 이름. 툴팁이 "A → B"를 만들 때 쓴다.
public let firstSprintName: String?
/// 가장 늦은 스프린트 이름.
public let latestSprintName: String?
```

배열 전체를 저장하지 않는 이유: 표시에 필요한 것이 이 셋뿐이고, 13개 × 수백 건의 이름
목록은 미러를 눈에 띄게 키운다. 나중에 "어느 스프린트들이었나"를 보여줄 일이 생기면
그때 넓힌다.

**SwiftData 마이그레이션:** 세 프로퍼티 모두 **선언에 기본값을 붙인다**(`= 0`, `= nil`).
`IssueEventRecord.origin`과 같은 이유다 — SwiftData는 기존 로우를 복원할 때 커스텀 `init`을
부르지 않으므로, `init` 파라미터 기본값만으로는 이 컬럼이 없던 레코드를 열 수 없다.

## 5. 이월 횟수 계산

```swift
public struct SprintSummary: Sendable, Equatable {
    public let carryOvers: Int
    public let firstName: String?
    public let latestName: String?
}

public enum SprintHistory {
    /// 스프린트 배열에서 이월 횟수와 양 끝 이름을 뽑는다.
    ///
    /// **배열은 시간순이 아니다.** 실측에서 [56, 57, 55, 64, 63, 52, 65, 62, 60, 61, 59, 58, 66]
    /// 순으로 왔다. `startDate`로 정렬해야 첫·마지막이 맞는다.
    public static func summarize(_ sprints: [JiraSprint]) -> SprintSummary
}
```

- **이월 횟수 = 스프린트 수 - 1.** 첫 스프린트는 이월이 아니다. 0개나 1개면 0이다.
- **정렬은 `startDate` 오름차순.** 동률이면 `id`로 가른다 — Swift의 `sorted(by:)`는 안정
  정렬이 아니고, 같은 날 시작한 스프린트 둘이 있으면 툴팁이 실행마다 바뀐다.
- `startDate`가 없는 스프린트(드물지만 가능)는 정렬에서 맨 뒤로 보낸다. 버리지는 않는다 —
  횟수에는 들어가야 한다.
- `state`(`closed`/`future`/`active`)는 **구분하지 않는다.** 예정 스프린트에 올라가 있다는 것도
  "아직 안 끝났다"는 같은 이야기다.

## 6. 화면

`BoardSlot`은 **사실만** 싣는다 — `sprintCarryOvers: Int`와 `firstSprintName`/`latestSprintName`.
`"모비닥 스프린트 (52) → 모비닥 스프린트 (66)"` 같은 **문장은 뷰가 조립한다.**

`DueState`가 이미 같은 경계를 쓴다 — `ArcadeCore`는 `.dueIn(days: 3)`이라는 사실을 담고
"D-3"이라는 표현과 언제부터 강조할지는 뷰가 정한다. `HygieneNextStep`도 마찬가지다
(`HygieneCalculator`의 doc-comment가 그 경계를 명시한다). 문자열을 `ArcadeCore`에서 만들면
그 모듈이 화면을 알게 되고, 세 곳이 서로 다른 규칙을 갖게 된다.

`BoardLayout`은 `ObservedIssue`의 값을 그대로 옮길 뿐 새 판단을 하지 않는다.

- **0회면 줄을 그리지 않는다.** 대부분의 티켓이 0이고, "스프린트 0회"는 아무것도 말하지 않으면서
  카드만 어지럽힌다.
- 카드 높이 예산은 이미 빠듯하다(실패 상태에서 96pt 중 92pt 사용). 이월 줄은 **대기·실패
  블록이 없을 때만** 그린다 — 그 둘은 그 순간 행동을 요구하는 정보이므로 우선한다.
- 색은 `inkTertiary`. 이월은 사실이지 경고가 아니다. 등급 배지가 이미 위험을 말하고 있고,
  같은 카드에 두 번째 경고색을 넣으면 어느 쪽을 봐야 할지 흐려진다.

## 7. 실패와 빈 값

| 상황 | 처리 |
|---|---|
| 스프린트 필드를 못 찾음 | 이월 표시 없음. 경고 없음 |
| `/field` 조회 실패 | 이월 표시 없음. 다음 로그인에서 다시 시도 |
| 티켓에 스프린트가 없음 (`null`) | 0회 — 줄을 그리지 않음 |
| 스프린트가 하나뿐 | 0회 — 줄을 그리지 않음 |
| 배열 원소 디코딩 실패 | 그 원소만 건너뛴다. 배열 전체를 버리지 않는다 |

마지막 항목은 `JiraSearchResponse`가 이슈 단위로 이미 쓰는 방식과 같다 — 하나가 깨져도
나머지를 살린다.

## 8. 테스트 전략

| 계층 | 무엇을 |
|---|---|
| `ArcadeCoreTests` | `SprintHistory.summarize` — 뒤섞인 배열 정렬, 0/1개, `startDate` 없음, 동률 타이브레이크 |
| `JiraKitTests` | 스프린트 배열 디코딩, 원소 하나 깨졌을 때 나머지 보존, 필드 목록에서 `gh-sprint` 스키마 찾기 |
| `ArcadeAppTests` | 필드 ID 저장/로드, 계정 전환 시 폐기, 못 찾았을 때 degrade |
| `ArcadeUI` | 타깃 없음. 0회일 때 줄이 없는지는 소스 검사로 |

**필드 식별 테스트가 이 계획에서 가장 중요하다.** 이름이 아니라 `schema.custom`으로 찾는지를
고정한다 — 픽스처에 이름이 `"스프린트"`인 필드를 넣어, 영어 이름을 찾는 구현이면 실패하게 한다.

## 9. 스코프 경계

### 포함

1. `/rest/api/3/field`에서 스프린트 필드 ID 조회와 저장
2. 동기화 응답에서 스프린트 배열 파싱
3. `SprintHistory.summarize` — 이월 횟수와 양 끝 이름
4. `ObservedIssue`/`IssueSnapshot` 확장과 마이그레이션
5. 카드에 이월 줄과 툴팁

### 제외

| 제외 항목 | 이유 |
|---|---|
| 스프린트별 레인·필터 | 활성 스프린트가 없는 조직에서 만들 화면이 아니다(§1 ②) |
| 이월을 XP·위생에 반영 | 보스전이 정체일로 같은 일을 한다. 표시가 쓸모 있는지 본 뒤 판단 |
| 이월을 이벤트 로그에 기록 | Jira가 완전한 이력을 갖고 있어 diff로 잡을 이유가 없다(§1.1) |
| 스프린트 목표(`goal`) 표시 | 실측 데이터에서 전부 빈 문자열이었다 |
| 보드 여러 개 다루기 | 실측에서 `boardId`가 전부 17로 하나였다. 여러 보드가 나오면 그때 |
| Agile API | 필요 없다(§1 ①) |

## 10. 완성 정의

```
□ 로그인하면 스프린트 필드 ID를 한 번 조회해 저장한다
□ 필드 이름이 "Sprint"가 아닌 사이트에서도 찾는다
□ 여러 스프린트를 거친 티켓의 카드에 이월 횟수가 뜬다
□ 툴팁에 첫·마지막 스프린트 이름이 시간순으로 뜬다
□ 스프린트가 없거나 하나뿐인 티켓에는 줄이 없다
□ 스프린트를 쓰지 않는 사이트에서도 앱이 정상 동작하고 경고가 없다
□ 기존 미러가 있는 상태에서 앱을 올려도 열린다 (마이그레이션)
□ XP·레벨·위생 값이 이 계획 전후로 동일하다
□ swift test 전부 통과
```

마지막에서 두 번째 항목이 이 계획의 안전장치다. 표시만 더하기로 했으므로 **채점 결과가
바뀌면 그것이 결함**이다.

## 11. 리스크

| 리스크 | 완화책 |
|---|---|
| 다른 사이트의 스프린트 필드 스키마가 다르다 | `schema.custom`은 Atlassian이 오래 유지해온 값이다. 못 찾으면 표시를 끄고 나머지는 돈다 |
| 스프린트 배열이 큰 티켓이 많아 응답이 커진다 | 실측 최대 13개, 원소당 8필드. 티켓 49건 기준 무시할 크기다 |
| 이월 횟수와 정체일이 서로 다른 이야기를 한다 | 그것이 정보다. 정체일은 마지막 움직임 이후, 이월은 계획 대비 지연 — 둘이 갈리는 티켓이 오히려 눈여겨볼 대상이다 |
| 카드가 더 빡빡해진다 | 0회는 안 그리고, 대기·실패 블록이 있으면 양보한다(§6) |

## 12. 결정 기록

| 결정 | 채택 | 대안 | 이유 |
|---|---|---|---|
| 데이터 출처 | 기존 `/search/jql` 응답 | Agile API | 스프린트 필드가 이미 온다. `AuthProvider` 계약 변경이 불필요해진다 |
| 기능 형태 | 카드에 이월 횟수 | 스프린트 보드 화면 | 활성 스프린트가 0건인 조직에서 "현재 스프린트" 화면은 성립하지 않는다 |
| 필드 식별 | `schema.custom` | 필드 이름 `"Sprint"` | 실측 사이트의 이름이 `"스프린트"`였다. 이름은 로케일에 따라 다르다 |
