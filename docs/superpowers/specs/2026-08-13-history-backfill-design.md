## 1. 배경

v0.1 스펙은 "관측을 시작한 날부터의 역사만 존재한다"를 명시적으로 선택했고, changelog 소급 복원을 §10에서 제외했다. 이유는 초기 동기화 지연과 에러 경로 증가였고, "LV.1 시작이 게임적으로 자연스럽다"고 판단했다.

이 문서는 **그 결정을 뒤집는다.** 사용자가 과거 이력을 XP·레벨에 전부 소급하기로 결정했다.

### 1.1 실측 (2026-08-13 조회)

| 항목 | 값 |
|---|---|
| 담당한 전체 티켓 | 1,263건 |
| 그중 완료 | 1,215건 |
| 이력 기간 | 2022-12-30 ~ 현재 (약 3년 8개월) |
| 최근 1년 내 완료 | 137건 |
| 담당 티켓의 프로젝트 분포 | DEMO 1,262건 / 그 외 1건 |
| 조회 가능한 프로젝트 | 17개 |

**최근 1년이 137건뿐**이라는 분포가 이 설계의 핵심 제약이다. 1,215건을 그대로 XP로 환산하면 시작 레벨이 40~50이 되고, 이후 주당 5건은 레벨바를 거의 움직이지 못한다. 게임화가 유도하려던 행동에 대한 피드백이 죽는다. §6의 시즌 도입이 이 문제를 다룬다.

### 1.2 changelog 샘플에서 드러난 세 가지 사실

가장 오래된 티켓 하나의 changelog를 조회해 확인했다.

**① 과거 워크플로 상태명이 현재와 다르다.** 전이 경로가 `To Do → 진행 중 → 스테이징 병합 → 스테이징 배포 → 검수완료 → Done`인데, 현재 `WorkflowMap.demo`에는 `To Do`·`스테이징 병합`·`검수완료`·`Done`이 없다. 3년 8개월 사이 워크플로가 개편됐다. 매핑되지 않은 상태 전이는 현재 규칙상 0점이므로, 그대로 소급하면 과거 XP의 상당 부분이 사라진다.

확인 결과 이 상태들은 **삭제된 것이 아니라 워크플로에서 빠졌을 뿐**이다(`스테이징 병합` 6건, `검수완료` 1건이 현재도 존재). 따라서 `statusCategory` 조회로 폴백할 수 있다.

**② 전이를 실행한 사람이 담당자가 아닌 경우가 많다.** 샘플 티켓의 status 전이 5건 중 3건을 다른 사람이 실행했다. changelog는 `author.accountId`를 주므로 구분할 수 있다 — 현재의 diff 관측 방식으로는 알 수 없던 정보다.

**③ changelog는 노이즈가 크다.** 10개 history 중 status는 5건이고, 나머지는 description 수정·링크·Fix Version이다. description 변경은 본문 전체를 from/to 양쪽에 실어 응답 크기를 키운다.

## 2. 확정된 결정

| 결정 | 선택 | 기각한 대안 |
|---|---|---|
| 소급 범위 | **XP·레벨에 전부 소급** (3년 8개월 전체) | 별도 통산 기록만 / 기간 절단 / 지표 정확도만 개선 |
| 전이 주체 | **내가 직접 옮긴 것만 XP** | 담당 티켓의 모든 전이 / 가중치 분배 |
| 진행 방식 | **2단계 분리** — 2b-1 백필 → 2b-2 진행형 전환 | 한 번에 changelog 단일 소스로 / 소급만 하고 진행형은 영구히 diff |
| 워크플로 폴백 | **statusCategory 폴백 + 마법사 제출** 병행 | 과거 상태 무시 |
| 둔화 완화 | **시즌 도입** | XP 시간 감쇠 / 레벨 곡선 조정 |
| 프로젝트 범위 확장 | **이 계획에서 제외** (계획 2c) | 함께 진행 |

### 2.1 왜 2단계로 나누는가

"내가 직접 옮긴 것만"을 택하면 현재 동기화 로직도 틀린 것이 된다. diff 관측은 실행자를 알 수 없어 `actorAccountId`에 담당자를 넣기 때문이다. 올바른 종착지는 **changelog가 상태 전이의 단일 진실 소스가 되는 것**이지만, 한 번에 가면 계획이 너무 커진다.

백필은 미지의 영역이 많다(1,263건 페이지네이션, 재개, 3년 전 워크플로, rate limit). 실물에서 검증한 뒤 진행형을 옮기는 편이 안전하다.

**그 사이 기간의 불일치를 명시한다:** 백필 구간은 실행자 기준, 관측 구간은 담당자 기준으로 채점된다. 의도된 임시 상태이며 설정 화면의 진단 정보에 "관측 구간 전이는 실행자를 구분하지 않습니다"로 표시한다. 계획 2b-2에서 해소한다.

## 3. 이벤트 로그 무결성

백필은 이벤트 로그에 쓰는 **두 번째 작성자**다. 지금까지 `DiffEngine`이 유일했기에 append-only가 자연히 지켜졌으나, 백필이 들어오면 같은 전이를 두 번 기록할 위험이 생긴다.

```
      ┌────────────── 이벤트 로그 (append-only) ──────────────┐
      │                                                      │
 DiffEngine                                        BackfillEngine
 (기존, 5분 폴링)                                  (신규, 일회성)
   appeared / touched                               statusChanged
   vanished / dueDateChanged                        (changelog에서)
   statusChanged ← 2b-2에서 이관
```

### 3.1 IssueEventRecord에 추가하는 두 필드

```swift
/// Jira changelog history의 고유 id. 백필로 만든 이벤트만 값이 있다.
/// 같은 전이를 두 번 기록하지 않기 위한 유일한 근거다 — 시각·상태명 비교로
/// 추측하지 않는다(같은 초에 두 전이가 일어날 수 있고, 왕복 전이는 값이 같다).
var sourceHistoryId: String?

/// 이 이벤트의 출처. "observed"(diff 관측) 또는 "backfill"(changelog).
var origin: String
```

**`origin`이 필요한 이유:** `ArcadeStore.observationDayCount(now:)`는 첫 성공 동기화 이후 일수를 센다. 백필 이벤트가 섞이면 이 값이 3년 8개월로 뛰고, 그러면 정체 판정이 "근사 기준"에서 "정확 기준"으로 잘못 승격되며 UI의 "관측 N일차"도 거짓이 된다. **관측 일수는 `origin == "observed"`만 센다.**

**마이그레이션:** 두 필드 모두 lightweight migration으로 처리한다. `sourceHistoryId`는 옵셔널이라 조건을 자동 충족하고, `origin`은 **프로퍼티 선언 자체에** 기본값을 붙여야 한다:

```swift
public var origin: String = EventOrigin.observed
```

이니셜라이저 파라미터의 기본값(`init(… origin: String = EventOrigin.observed)`)으로는 **부족하다.** SwiftData가 디스크의 기존 로우를 모델로 복원할 때는 커스텀 `init`을 호출하지 않고 자체 디코딩 경로를 쓰므로, `init`에만 있는 기본값은 참조되지 않는다. `@Model` 매크로가 스키마를 만들 때 읽는 것은 프로퍼티 선언에 직접 붙은 리터럴이다.

두 종류의 기본값을 혼동하기 쉽고, **인메모리 컨테이너 테스트는 이 차이를 드러내지 못한다** — 매번 새 스토어를 만들므로 "기존 로우를 여는" 경로를 지나지 않는다. 실제 검증은 이전 스키마로 만든 파일 기반 컨테이너를 열어야 한다.

이벤트 로그는 절대 지우지 않는다(v0.1 스펙 §8.6).

## 4. changelog를 이벤트로 번역

### 4.1 필드 매핑

`histories[].items[]` 중 `field == "status"`인 항목만 이벤트가 된다.

```
history.created           → observedAt        (전이가 실제로 일어난 시각)
history.id                → sourceHistoryId
history.author.accountId  → actorAccountId
item.fromString           → fromStatus
item.toString             → toStatus
item.from / item.to       → 상태 ID (폴백 조회에 사용)
```

`observedAt`은 **전이 시각**이지 백필 실행 시각이 아니다. 이걸 틀리면 3년치 이벤트가 전부 오늘로 몰려 시즌 계산과 정체 판정이 무너진다.

### 4.2 남이 옮긴 전이도 기록한다 — XP만 0

| | 이벤트 기록 | XP |
|---|---|---|
| 내가 옮긴 전이 | ○ | ○ |
| 남이 옮긴 전이 | ○ (`actorAccountId`에 그 사람) | **0** |

**기록하는 이유는 `statusEnteredAt` 때문이다.** "이 티켓이 현재 상태에 언제 들어갔나"는 누가 옮겼든 갱신돼야 정확하다. 남이 옮긴 전이를 버리면, 내가 `진행 중`으로 옮긴 뒤 QA가 `검수완료`로 옮긴 티켓의 기준선이 내 전이 시각에 멈춰 **정체일이 부풀려지고**, 나중에 그 티켓을 건드릴 때 보스전 XP가 과대 지급된다.

`XpAwarder`에 규칙 한 줄을 추가한다: `actorAccountId != myAccountId`면 0. `RuleSet.awardsOnlyOwnTransitions: Bool = true`로 두어 나중에 바꿀 수 있게 한다.

### 4.3 백필도 "채점은 이벤트 로그만의 함수" 불변식을 지킨다

계획 1의 최종 리뷰에서 확립된 불변식이 있다: **채점은 (이벤트 로그, RuleSet)만의 함수여야 하고 미러에 의존해서는 안 된다.** 미러의 `jiraUpdatedAt`은 재집계 직전에 최신값으로 덮이므로 정체 기준선으로 쓸 수 없고, 조회 결과에서 사라진 티켓은 미러에서 없어져 마감 보너스가 증발하기 때문이다. 그래서 `DomainEvent`가 두 값을 직접 들고 다닌다:

- `priorUpdatedAt` — 이 변화 **직전**의 `jiraUpdatedAt`. 정체 기준선.
- `dueDateAtObservation` — 관측 **시점의** 마감일. 마감 전 완료 보너스가 이 값을 본다.

백필이 만드는 이벤트도 이 두 필드를 채워야 한다. 그러지 않으면 소급 XP가 미러 상태에 따라 달라져 불변식이 깨진다.

**changelog에서 두 값을 복원하는 방법:**

| 필드 | 복원 방법 |
|---|---|
| `priorUpdatedAt` | **직전 history의 `created`.** 티켓의 모든 변경이 changelog에 남으므로, 어떤 전이 직전의 마지막 수정 시각은 곧 그 앞 history의 시각이다. 첫 history라면 직전 변경이 없으므로 `fields.created`(티켓 생성 시각)를 쓴다. |
| `dueDateAtObservation` | changelog에서 `field == "duedate"`인 항목을 모아 시간순으로 훑으면 각 시점의 마감일을 재구성할 수 있다. 변경 이력이 없으면 현재 `fields.duedate`가 그 시점에도 같았다는 뜻이다. |

이 복원이 오히려 관측보다 **정확하다.** 관측은 5분 폴링 사이에 일어난 중간 전이를 놓치지만 changelog는 전부 남긴다. 즉 백필 구간의 정체 기준선은 근사가 아니라 정확값이며, 스펙 §5.2가 말한 "이벤트가 쌓이면 정확한 기준으로 승격"이 백필로 즉시 달성된다.

## 5. 워크플로 폴백 (3단)

```
상태 만남
   │
   ├─① WorkflowMap에 있나?           → 그 Stage 사용 (정확)
   ├─② /rest/api/3/status에 있나?     → statusCategory로 폴백
   │      To Do → backlog · In Progress → active · Done → done
   └─③ 둘 다 없음                     → unmapped (XP 0) + 마법사 후보로 수집
```

**②의 조회는 일회성이다.** `GET /rest/api/3/status`가 모든 상태의 `id`·`name`·`statusCategory`를 한 번에 준다. 백필 시작 시 한 번 받아 캐시한다. changelog에는 상태 ID와 이름이 둘 다 있으므로 **ID로 매칭한다** — 이름은 바뀔 수 있지만 ID는 안 바뀐다.

**②가 0점보다 나은 이유:** `스테이징 병합 → 스테이징 배포` 전이에서 `스테이징 병합`이 매핑에 없어 0점 처리하면 그 전진이 통째로 사라진다. `statusCategory`가 `In Progress`라면 `active`로 떨어뜨려 `active → review` 전진으로 채점된다. 정확도는 낮지만 방향은 맞다.

**③이 ①로 되돌아온다.** 백필이 끝나면 발견한 미매핑 상태를 매핑 마법사 후보로 제출한다(`discoveredFromHistory` 표시). 사용자가 확정하면 **재집계로 소급 XP가 정확해진다** — 이벤트 로그가 원본이고 점수는 파생이기에 가능하다.

**한계:** `스테이징 병합`과 `스테이징 배포`이 둘 다 `In Progress`면 같은 `active`로 떨어져 그 사이 전이가 "수평 이동 = 0점"이 된다. 마법사 확정 전까지는 일부 전진이 0점이다.

## 6. 시즌 — 소급의 부작용 완화

레벨을 두 개 둔다.

| | 계산 범위 | 표시 위치 |
|---|---|---|
| **통산 레벨** | 전체 이벤트 로그 | 프로필 |
| **시즌 레벨** | 최근 30일 이벤트 (**롤링 윈도우**) | HUD의 XP 바 |

**시즌은 고정 기간이 아니라 롤링 윈도우다.** "매월 1일에 리셋"이 아니라 항상 `now - 30일`부터를 센다. 고정 시즌은 리셋 직후 XP 바가 0이 되어 "어제까지의 성과가 사라진" 느낌을 주고, 리셋 날짜를 사용자가 기억해야 한다. 롤링은 매일 조금씩 빠지고 조금씩 들어오므로 그런 절벽이 없다.

소급의 목적("그동안 한 일이 인정됨")과 게임의 목적("오늘 하나 처리한 것이 보임")을 둘 다 만족한다.

**구현이 싼 이유:** `ScoreEngine.recompute`는 이벤트 배열을 받아 처음부터 계산하는 순수 함수다. 시즌은 `since: Date?` 파라미터 하나를 더해 이벤트를 필터링하면 끝난다. XP를 누적 저장하는 구조였다면 "최근 30일 XP"를 별도 관리해야 했고 둘이 어긋나는 버그가 생겼을 것이다.

시즌 길이(30일)는 `RuleSet.seasonDays`로 외부화한다. 시즌 랭킹·리더보드는 이 계획에 넣지 않는다(경쟁 요소는 팀 판과 함께, 계획 2c).

## 7. 백필 실행 모델

### 7.1 규모와 호출

1,263건을 `/search/jql` + `expand=changelog`로 100건씩 조회 → **13회**.

**함정:** expand로 오는 changelog에는 자체 페이지네이션이 있다.

```json
"changelog": { "startAt": 0, "maxResults": 10, "total": 10, "histories": [...] }
```

`total > histories.count`인 티켓은 `/issue/{key}/changelog`로 따로 채운다. 이 검사를 빠뜨리면 history가 많은 오래된 티켓의 전이가 조용히 누락되고, **누락은 에러가 아니라 "점수가 조금 적게 나오는" 형태로만 드러나** 알아채기 어렵다.

### 7.2 재개

```swift
@Model final class BackfillRun {
    var startedAt: Date
    var finishedAt: Date?
    var jql: String                        // 어떤 범위를 백필했는지
    var nextPageToken: String?             // 여기서 재개
    var processedIssueCount: Int
    var totalIssueCount: Int
    var discoveredUnmappedStatuses: [String]
    var partiallyRestoredKeys: [String]    // changelog 보충 조회에 실패한 티켓
    var failureMessage: String?
}
```

`nextPageToken`을 매 페이지 저장하므로 중단 지점부터 이어진다. `sourceHistoryId` 중복 검사가 있어 **겹쳐 훑어도 안전하다** — 재개 지점을 정확히 맞출 필요가 없다.

### 7.3 실행과 표시

- **사용자가 누른다.** 설정에 "과거 기록 불러오기" 버튼. 자동 실행은 하지 않는다 — 첫 로그인 직후 수십 초 네트워크 점유를 설명 없이 겪게 할 일이 아니다.
- 아케이드 플로어에 진행 바: "과거 기록 불러오는 중 340/1,263".
- 백필 중에도 앱은 정상 동작한다. 이벤트가 append될 뿐이라 기존 화면이 막힐 이유가 없다.
- 완료 후 `ScoreEngine.recompute`를 **두 번** 돌린다 — 통산(`since: nil`)과 시즌(`since: now - seasonDays`). 같은 이벤트 로그를 두 범위로 집계하는 것이므로 두 호출은 서로 독립이고, 멱등성은 계획 1 Task 10에서 이미 테스트로 고정돼 있다.

### 7.4 미러는 건드리지 않는다

완료된 1,215건을 미러에 넣으면 DB가 25배가 되고 "내 티켓" 화면에 완료가 섞인다. **이벤트만 넣는다.** `ScoreEngine`이 미러에 없는 티켓의 이벤트를 `placeholder(for:)`로 이미 처리한다 — 계획 1에서 "미러에서 사라진 티켓의 과거 이벤트도 점수에 남아야 한다"고 대비해둔 코드가 이 경우를 그대로 받는다.

## 8. 에러 처리

| 실패 | 처리 |
|---|---|
| 네트워크 중단·앱 종료 | `nextPageToken`으로 다음 실행에서 "이어서 불러오기" 제안 |
| 429 rate limited | `Retry-After` 존중해 대기 후 같은 토큰으로 재시도 |
| 개별 티켓 changelog 조회 실패 | 그 티켓만 스킵하고 `partiallyRestoredKeys`에 기록. 나머지 계속 |
| `/status` 조회 실패 | 폴백 ② 불가 → ①③만으로 degraded 진행 + "일부 과거 상태를 분류하지 못했습니다" 표시 |
| changelog 보충 조회 실패 | 해당 티켓을 "부분 복원"으로 기록하고 진행 |

**부분 실패를 전체 실패로 만들지 않는다**(v0.1 스펙 §8.4 계승). 1,263건 중 3건이 실패했다고 나머지를 버리지 않는다.

**백필은 기존 데이터를 손상시킬 수 없다.** append-only이고 중복 검사가 있으므로 최악의 경우도 "이벤트가 덜 들어갔다"이다. 중간에 죽어도 이미 넣은 이벤트는 유효하고, 재실행하면 겹치는 구간을 안전하게 건너뛴다.

## 9. 테스트 전략

무게중심은 순수 함수다. `ChangelogParser`가 "JSON → 이벤트 배열"이라 계획 1의 규칙 엔진과 같은 방식으로 검증된다.

| 영역 | 반드시 통과할 것 |
|---|---|
| 파싱 | `field == "status"`만 이벤트가 된다 (description·Link·Fix Version은 버려진다) |
| 파싱 | `history.created`가 `observedAt`이 된다 — 백필 실행 시각이 아니다 |
| 불변식 | `priorUpdatedAt`이 **직전 history의 created**로 채워진다. 첫 history면 `fields.created` |
| 불변식 | `dueDateAtObservation`이 그 시점의 마감일로 채워진다 (duedate 변경 이력 반영) |
| 불변식 | 미러를 비워도 백필 이벤트의 XP가 변하지 않는다 (채점이 이벤트만의 함수) |
| 중복 | 같은 `sourceHistoryId`를 두 번 넣으면 이벤트는 1개 |
| actor | 남이 옮긴 전이 → 이벤트 기록 ○, XP 0 |
| actor | 남이 옮긴 전이도 `statusEnteredAt`을 갱신한다 (정체일이 부풀지 않는다) |
| 폴백 | ①→②→③ 순서. `statusCategory`가 `In Progress`면 `active` |
| origin | `observationDayCount`가 백필 이벤트를 세지 않는다 |
| 시즌 | `since` 필터가 통산과 다른 값을 낸다. 경계에 걸친 이벤트가 한 번만 센다 |
| 재개 | `nextPageToken` 저장 → 복원 → 겹쳐 훑어도 이벤트 총량이 같다 |
| 페이지네이션 | `total > histories.count`를 감지해 추가 조회한다 |
| 마이그레이션 | 기존 이벤트가 `origin = "observed"`로 채워지고 하나도 사라지지 않는다 |

**fixture 정책:** 실제 changelog **구조**(중첩된 `histories[].items[]`, author, from/to/fromString/toString)를 그대로 쓴다. 다만 **상태명은 실제 값을 쓰지 않는다** — 계획 2a에서 저장소의 조직 상태명을 모두 제거하고 테스트용 `demoWorkflow`(`To Do`/`In Progress`/`In Review`/`Verifying`/`Done`)로 대체했으며, 그 관례를 따른다.

폴백 테스트가 필요로 하는 것은 "현재 매핑에 없는 과거 상태"라는 **성질**이지 특정 문자열이 아니다. 가상의 과거 상태명(`Merged to Staging`, `QA Passed`)이 그 역할을 똑같이 수행하며, 조직 정보를 저장소에 남기지 않는다. 사람 이름·accountId·티켓 요약·조직 호스트도 예시 값으로 바꾼다.

## 10. 스코프 경계

### 포함

1. `ChangelogParser` — changelog JSON → `DomainEvent` (순수 함수)
2. `IssueEventRecord`에 `sourceHistoryId`·`origin` 추가 + SwiftData 마이그레이션
3. 3단 워크플로 폴백 + `/rest/api/3/status` 조회·캐시
4. `BackfillEngine` + `BackfillRun` (재개·진행률·부분 실패 수집)
5. changelog 자체 페이지네이션 감지 및 보충 조회
6. `XpAwarder`의 actor 필터 (`RuleSet.awardsOnlyOwnTransitions`)
7. 시즌 — `ScoreEngine.recompute(since:)`, 통산/시즌 레벨 분리
8. HUD에 시즌 XP 바, 프로필에 통산 레벨
9. 설정의 "과거 기록 불러오기" 버튼 + 진행 바 + 중단/재개
10. 백필이 발견한 미매핑 상태를 매핑 마법사 후보로 제출

### 제외

| 제외 | 이유 |
|---|---|
| 진행형 동기화의 changelog 전환 | 계획 2b-2. 백필을 실물에서 검증한 뒤 |
| 프로젝트 범위 확장·팀 판 | 계획 2c. 팀 판 화면 설계와 함께 |
| 완료 티켓을 미러에 저장 | 이벤트만 넣는다(§7.4) |
| 시즌 랭킹·리더보드 | 시즌 레벨만. 경쟁 요소는 계획 2c |
| 백필 자동 실행 | 사용자가 누른다 |
| XP 시간 감쇠 | 시즌으로 해결됐다 |

### 완성 정의

```
□ 백필 버튼을 누르면 1,263건을 훑고 진행률이 보인다
□ 중간에 앱을 껐다 켜면 이어서 불러온다
□ 두 번 돌려도 이벤트가 중복되지 않는다 (sourceHistoryId)
□ 남이 옮긴 전이는 기록되지만 내 XP를 올리지 않는다
□ 과거 상태(스테이징 병합·검수완료)가 statusCategory로 분류돼 0점이 아니다
□ 미매핑 상태가 마법사 후보로 올라오고, 확정 후 재집계하면 점수가 정확해진다
□ HUD의 XP 바는 최근 30일, 프로필의 레벨은 통산
□ "관측 N일차"가 백필 때문에 3년으로 뛰지 않는다
□ swift test 전부 통과, 경고 0
```

## 11. 리스크

**1. 백필 후 시작 레벨이 예상과 다를 수 있다.** 백필 대상은 완료 1,215건이 아니라 **담당한 전체 1,263건**이다(미완료 48건에도 과거 전이가 있다). 그러나 남이 옮긴 전이를 0점 처리하므로 실제 소급 XP는 티켓 수가 시사하는 것보다 상당히 적을 수 있다 — 샘플 티켓은 status 전이 5건 중 본인이 한 것이 2건이었다. 이 비율이 전체에도 비슷하다면 소급 XP는 절반 이하가 된다. 결함이 아니라 선택한 규칙의 결과이며, 백필을 돌려봐야 실제 숫자를 알 수 있다.

**2. 429가 걸릴지 미지수다.** 13회 호출이면 안 걸릴 것으로 보이나 changelog 보충 조회가 수십 건 발생하면 달라진다. 백오프는 넣되 실측이 필요하다.

**3. `statusCategory` 폴백의 정확도 한계.** 같은 카테고리로 떨어지는 두 상태 사이의 전이는 수평 이동(0점)이 된다(§5).

**4. 기준 불일치가 2b-2까지 남는다.** 백필 구간은 실행자 기준, 관측 구간은 담당자 기준(§2.1). 설정 화면에 명시한다.
