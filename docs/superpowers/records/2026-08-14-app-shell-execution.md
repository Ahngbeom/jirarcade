# 계획 2a(앱 셸) 실행 기록

브랜치 `feature/app-shell` · 16개 태스크 · 최종 221 tests · 경고 0

이 문서는 실행 중 컨트롤러가 사용자를 대신해 내린 판정과, 리뷰가 찾아낸 결함을
기록한 것이다. 왜 코드가 지금 모양인지에 대한 답이 여기 있다.

## 컨트롤러 판정 (28건)

각 판정은 근거와 "틀렸을 경우 비용"을 함께 기록했다. 비용이 "없음"이 아닌 것부터 보면 된다.

**Task 1** — `backoffDelay`의 guard를 `let last = backoffSteps.last` → `!backoffSteps.isEmpty`로 바꾼 구현자의 편차를 인정한다 — 계획 원문의 `last`는 이후 쓰이지 않아 미사용 변수 경고를 내고, Global Constraints의 "경고 0"이 태스크 본문보다 우선한다. 두 가드는 동일한 것(빈 배열)을 막고 시그니처·동작이 같다. 계획 문서도 같은 값으로 고쳐 재발을 막았다
  · *틀렸을 경우 비용:* 없음(두 형태가 의미상 동일하므로 되돌려도 동작 변화 없음).

**Task 1** — `Cabinet.accentToken: String`이 v0.1 스펙 §3.1의 `accent: Color`와 다르지만 토큰 형태를 유지한다 — 캐비닛이 `Color`를 보유하면 (1) 색 값을 캐비닛이 결정하게 되어 라이트/다크 전환이 캐비닛을 지나치고, (2) 캐비닛은 `ArcadeTheme`을 주입받지 않으므로 Color를 만들려면 리터럴을 써야 해서 "ArcadeUI 뷰 코드에 색 리터럴 금지" 제약이 캐비닛에서 깨진다. v0.1 §3.1은 테마 시스템 설계 이전의 스케치다. v0.1 스펙 문서를 구현에 맞춰 갱신했다. `@MainActor`도 메서드 단위 → 프로토콜 전체로 올렸다
  · *틀렸을 경우 비용:* 토큰이 String이라 오타를 컴파일러가 못 잡는다. 나중에 `PaletteTokens`의 키를 enum으로 승격하면 타입 안전성을 되찾을 수 있고, 그 변경은 캐비닛 구현체 하나(2a 기준)만 건드린다.

**Task 2** — `color(forToken:)`의 `default: inkSecondary`를 없애고 `PaletteTokens.hex`에 위임한다 — 리뷰어 지적이 맞다. 같은 파일의 hex 파싱은 잘못된 입력에 fatalError인데 토큰 조회만 조용히 그럴듯한 색을 돌려주고, 4개 토큰만 처리해 `surfaceBase`·`line`·`inkPrimary`·`inkTertiary` 같은 **유효한** 토큰도 default로 샌다. Task 14가 `cabinet.accentToken`을 이 경로로 넣으므로 소비되기 전에 고치는 게 맞다. 위임하면 switch 중복이 사라지고 전 토큰을 지원하며 오타는 크래시한다
  · *틀렸을 경우 비용:* 렌더링마다 hex를 다시 파싱한다. 캐비닛 수 개 규모라 무시 가능하고, 필요하면 나중에 딕셔너리로 캐시하면 된다.

**Task 2** — Minor(`ArcadeUI`가 `ArcadeCore`를 암묵 의존)를 같은 fix 라운드에 묶는다 — Minor는 원칙상 루프에 넣지 않지만 이건 `Package.swift` 한 줄이고 같은 태스크 범위이며 별도 라운드를 만들지 않는다. SwiftPM이 전이 의존을 import 가능하게 해줘 지금은 빌드되지만, 선언되지 않은 의존은 Task 16의 모듈 경계 테스트가 지키려는 바로 그 경계다
  · *틀렸을 경우 비용:* 없음(의존 선언을 명시하는 것은 되돌릴 필요가 없다).

**Task 3** — `transientPhasesAreNotWritable`이 `allowsWriting`만 검증해 `showsMirror`의 false 케이스가 `signedOut(nil)` 하나뿐이라는 리뷰어 지적을 받아들여 테스트를 고친다 — `showsMirror`를 `case .ready, .expired, .launching: true`로 변이해도 현재 스위트가 통과한다. `showsMirror`는 Task 10·14가 화면 분기에 쓰는 술어라 틀리면 "로그인 화면인데 캐비닛이 보인다"로 나타난다. 계획 원문의 테스트 코드에서 온 갭이므로 계획 문서도 함께 고쳤다
  · *틀렸을 경우 비용:* 없음(단언 한 줄 추가이고 통과 중인 동작을 바꾸지 않는다).

**Task 6** — 그 동시성 테스트를 정식 회귀 테스트로 추가한다 — 겹침 방지가 이 타입의 존재 이유인데 커밋된 스위트가 그것만 검증하지 않는다. Task 9가 이 스케줄러 위에 AppModel을 얹고, 거기서 중복이 나면 append-only 로그에 가짜 이벤트가 쌓인다. 점수가 그 로그의 순수 함수라 오염이 영구적이고, 크래시가 아니라 나중에 틀린 숫자로만 드러나며 어떤 이벤트가 가짜인지 구분할 방법이 없다
  · *틀렸을 경우 비용:* 테스트 하나가 늘어난다. 그뿐이다.

**Task 7** — `start()`의 `try? credentials.load()`를 do/catch로 바꿔 저장소 고장을 별도 메시지로 surface한다 — Task 4가 일부러 만든 "항목 없음 vs 실패" 구분을 소비 지점에서 버리고 있었다. `Phase.signedOut(message:)`에 이미 자리가 있어 비용이 거의 0이고, 뭉개면 사용자가 첫 실행과 고장을 구분할 수 없다
  · *틀렸을 경우 비용:* 없음(메시지 하나 추가이고 성공 경로는 그대로다).

**Task 7** — 유출 단언을 세 경로(invalidSite·unauthorized·catch-all) 전부에 넣는다 — 구현은 안전하지만 테스트가 `invalidSite`만 덮어, `.unauthorized` 경로에 토큰을 끼워 넣어도 아무 테스트가 실패하지 않는다. 자연스러운 실수가 나올 자리가 정확히 거기다
  · *틀렸을 경우 비용:* 없음(단언 추가).

**Task 7** — Minor 2건(`try? credentials.save` 삼킴, `?? nil` 죽은 표현식)을 같은 라운드에 묶는다 — 둘 다 같은 함수·같은 뿌리(SE-0230 평탄화와 try? 삼킴)이고 별도 라운드를 만들지 않는다. 단 `routeAfterAuthentication`의 `try? workflow.load()`는 유지한다 — 매핑 파일 부재는 진짜 첫 실행이고, Task 5의 저장소가 손상 파일에는 이미 throw한다
  · *틀렸을 경우 비용:* 없음.

**Task 7** — `credentialSaveWarning`에 전용 테스트가 없는 상태를 fix round 2로 만들지 않고 **Task 8 dispatch에 실어 보낸다** — 하네스(`InMemoryCredentialStore.saveError`)는 이미 있고 Task 8이 같은 두 파일(`AppModel.swift`, `AppModelTests.swift`)을 건드리므로, 라운드를 하나 더 돌리는 비용보다 다음 태스크에 얹는 편이 싸다. 재리뷰어가 접근 수준·리셋 시점·성공 경로 불변은 코드로 확인했으므로 무검증 상태로 방치되는 것은 아니다
  · *틀렸을 경우 비용:* Task 8이 그 지시를 놓치면 테스트 없는 동작이 남는다. Task 8 리뷰에서 확인한다.

**Task 8** — 리셋 가드의 세 번째 분기("이전 자격증명 읽기 실패 → 리셋 안 함")에 테스트를 추가한다 — 이 분기는 비대칭 위험에 근거한 의도적 선택인데(낡은 미러는 다음 동기화로 복구되지만 지워진 이벤트 로그는 복구 불가) 아무것도 고정하지 않는다. `loadError` 하네스가 이미 있어 비용이 낮고, `try?`를 `try`로 바꾸거나 "로드 실패 = 다른 계정"으로 뭉개는 변경이 조용히 통과한다
  · *틀렸을 경우 비용:* 테스트 하나. 단, 페이크의 `loadError`가 저장 경로까지 막으면 인증 전에 실패해 테스트가 엉뚱한 이유로 통과할 수 있다 — fix 지시에 그 확인을 넣었다.

**Task 9** — 이 유출을 지금 닫는다. 계획 1의 코드라 Task 9 범위 밖이지만 — (1) 디스크에 남는다. v0.1 스펙 §7이 자격증명을 Keychain에 두는 이유가 "앱 DB는 평문이며 백업에 딸려 나간다"이고, 그 DB에 이메일이 들어간다. (2) 노출 경로가 이미 문서화돼 있다 — `ArcadeStore.swift:145`가 `loadSyncRuns()`를 "진단 화면·테스트"용이라고 명시한다. 뒤 태스크가 그 화면을 만든다. (3) 아무 테스트도 지키지 않는다. 코드를 고쳐도 이미 쓰인 레코드는 사라지지 않으므로 화면을 만들기 전에 닫는 게 맞다. 설계: redaction을 `JiraKit`으로 올려 `ArcadeCore`·`ArcadeApp`이 같은 함수를 쓰게 한다 — 방어가 `JiraError` 옆, 기존 `invalidSite`의 "입력을 담지 않는다" 관례와 같은 자리에 산다
  · *틀렸을 경우 비용:* `JiraKit`에 공개 함수 하나가 늘고 `SyncEngine`의 진단 문자열이 케이스 이름으로 짧아진다. 실패 종류는 그대로 알 수 있다.

**Task 10** — 앱 타깃의 미선언 전이 의존을 고친다 — `JirarcadeApp`이 `["ArcadeUI"]`만 선언하면서 네 모듈을 import한다. 빌드는 되지만 SwiftPM이 모듈 검색 경로를 공유하는 부수 효과에 기댄 것이고, `Package.swift`가 의존 그래프의 진실한 기술이 아니게 된다. **같은 리포지토리에 선례가 있다**(8ab9739에서 `ArcadeUI`의 `ArcadeCore` 의존을 같은 이유로 명시)
  · *틀렸을 경우 비용:* 없음. 앱 타깃이 네 모듈을 아는 것 자체는 조립 지점이라 정상이고 선언만 맞춘다.

**Task 11** — 시각 검증을 기다리지 말고 커밋하되 **미검증을 명시**하게 한다 — 화면 잠금은 통제 밖이고 Task 12~15가 전부 시각 태스크라, 태스크마다 멈추면 코드와 무관한 이유로 계획 전체가 정지한다. 대신 리포트에서 "확인한 것"과 "확인 못 한 것"을 항목별로 가르게 했다. Task 15가 이미 전체 흐름 워크스루로 끝나고 Task 16이 완성 확인이므로, 누적된 시각 확인을 머신이 열렸을 때 그 지점에서 한 번에 수행한다
  · *틀렸을 경우 비용:* 화면이 잘못 그려진 채로 태스크 몇 개가 지나간다. Task 15·16에서 드러나고 거기서 고치면 된다. 기준을 낮추는 게 아니라 검증 시점을 옮기는 것이고, ledger와 최종 보고에 남기므로 조용히 사라지지 않는다.

**Task 11** — 이 경고 표시를 **Task 15에 싣는다** — Task 15가 이미 "에러 표시"를 다루고 (expired 배너, 연결 실패) 같은 성격의 경고를 하나 더 얹는 자리다. Task 13/14는 캐비닛과 플로어 레이아웃이라 성격이 다르다
  · *틀렸을 경우 비용:* 없음. Task 15에서 자리가 어색하면 거기서 다시 판단한다.

**Task 11** — (1)과 (2)를 **한 구조로** 고친다 — `phase`를 "진행 중"의 단일 진실 원천으로 삼아 `case .signedOut, .validating:`을 한 분기로 합치고 `SignInView`가 `isValidating`을 파라미터로 받게 한다. 뷰 정체성이 유지되어 `@State`가 살고, `AppModel.signIn`이 첫 `await` 전에 동기적으로 `.validating`을 설정하므로 재진입 창 자체가 없어진다(플래그 설정 순서에 기대지 않는다).   · *틀렸을 경우 비용:* 없음. 계획 문서에도 근거와 함께 반영해(aca906d) 나중에 "불필요한 합침"으로 되돌려지지 않게 했다.

**Task 13** — 프로토콜을 고쳐 `nonisolated var id`로 선언한다 — 지금 고치면 한 곳, 미루면 2b의 캐비닛마다 `: @MainActor Cabinet`을 반복해야 하고 빠뜨리면 원인을 짐작하기 어려운 에러가 난다. Task 14가 곧 이 프로토콜을 소비하므로 그 전에 닫는다
  · *틀렸을 경우 비용:* 없음(검증됨, 아래 참고).

**Task 13** — 빈 상태에 설명 한 줄을 넣는다 — "가짜 데이터를 만들지 마라"와 "비어 있다는 걸 말하라"는 다른 요구인데 내 dispatch가 전자만 강조해 후자가 빠졌다. 이 캐비닛의 일이 "지금 무엇을 아는가"에 답하는 것이므로, 비어 있다는 걸 말하지 않는 빈 상태는 그 일에 실패한다
  · *틀렸을 경우 비용:* 한 줄. 문구: "아직 동기화 전입니다. 첫 동기화가 끝나면 레벨과 경험치가 여기 나타납니다."

**Task 14** — 이 조정을 **Task 15에 싣는다** — Task 15가 이미 그 `.onChange` 블록을 수정하는 태스크이고(expired 배너·연결 실패·창 활성화 동기화), 같은 자리를 두 번 건드리지 않는 게 낫다
  · *틀렸을 경우 비용:* 만료 복구라는 드문 경로에서 동기화가 한 번 더 도는 것. 데이터 오염은 없다 (스케줄러가 겹침을 막고 diff는 멱등이다).

**Task 14** — 지금 고친다 — v0.1 스펙 §3이 "셸은 Cabinet 프로토콜만 안다"를 명시하는데, 2b에서 캐비닛을 추가하려고 이 파일을 고쳐야 한다면 그 속성은 애초에 없었던 것이다. YAGNI가 아닌 이유: 프로토콜은 이미 있고(Task 1) 준수도 돼 있다. **있는 추상화를 우회하던 것**을 고치는 것이지 없는 추상화를 만드는 게 아니다. 계획 작성 시 self-review에서 이 지점을 보고 "2a엔 캐비닛이 하나뿐이라 동작한다"고 넘겼는데 판단이 짧았다
  · *틀렸을 경우 비용:* 없음. 실제로 한 번에 컴파일됐고 배열 리터럴 한 줄이 늘었을 뿐이다.

**Task 15** — 현재 형태를 유지하고 우려를 기록한다 — (1) 논증이 현재 코드에 대해 정확하고 리뷰어가 검증한다, (2) `.onChange` 주석에 두 경로와 이유가 적혀 있어 세 번째 경로를 추가하는 사람이 그 주석을 만난다, (3) 대안인 `startSyncing()` 멱등화는 `SyncScheduler` 변경이라 Task 6의 동시성 테스트를 다시 봐야 하는데, 마지막 화면 태스크에서 손댈 범위가 아니다
  · *틀렸을 경우 비용:* 미래에 `.expired` 경로가 추가되면 만료 회복 시 동기화가 한 번 더 돈다. 데이터 오염은 없다(스케줄러가 겹침을 막고 diff는 멱등). 최종 리뷰에서 재판단 가능.

**Task 15** — 코드는 고치지 않고 **불변식을 코드 옆에 적는다** — 리포트의 경로 열거가 `.launching → .ready` 직행을 빠뜨렸지만 조건 자체는 그 경우에도 참이라 코드 결함이 아니다. 다만 콜그래프 의존이면 그것을 깨뜨릴 수 있는 변경을 하는 사람에게 알릴 방법이 주석뿐이다
  · *틀렸을 경우 비용:* 없음(주석 몇 줄).

**Task 15** — `signOut()`에 `stopSyncing()`을 넣는다 — 로그아웃 후에도 타이머가 무한히 돌며 매 틱 nil `client` 가드에서 no-op한다. 낭비이기도 하지만 더 중요하게 **로그아웃의 의미와 어긋난다**(사용자는 Jira와 말하지 말라고 했다)
  · *틀렸을 경우 비용:* 없음. 재로그인이 루프를 되살리는지 확인을 요구했고 구현자가 경로를 추적해 확인했다(`stop()`은 `loopTask`만 취소하고 스케줄러 인스턴스는 남으며 `start()`가 무조건 재생성한다).

**Task 15** — 백오프 상태 이월을 고친다 — Task 8이 "계정 전환 시 미러/이벤트 로그를 버린다"를 정했는데 스케줄러 상태가 그 목록에서 빠져 있었다. `signOut()`에서 `scheduler = nil`로 인스턴스를 버려 다음 `ensureScheduler()`가 깨끗한 것을 만들게 한다. `stop()` 안에서 리셋하지는 않는다 — `stop()`은 "기억하는 일시정지"로 남아야 미래에 이력을 잃지 않고 멈출 수 있다
  · *틀렸을 경우 비용:* 없음.

**Task 15** — 이 이슈를 Task 15에서 고치지 않고 **최종 전체 브랜치 리뷰로 넘긴다** — (1) Task 15의 두 finding은 ADDRESSED됐고 이건 선재 이슈다(라운드 1의 수정으로도 못 막았다), (2) 제대로 막으려면 `SyncEngine.sync()`가 store 쓰기 전에 취소를 확인해야 하는데 그건 `ArcadeCore`(계획 1 코드) 변경이고 Task 6의 동시성 테스트를 다시 봐야 한다, (3) 마지막 화면 태스크의 3라운드에서 손댈 범위가 아니고, 최종 리뷰가 전체 맥락으로 판단하는 게 낫다
  · *틀렸을 경우 비용:* 최종 리뷰에서도 놓치면 드문 조건에서 계정 간 데이터가 섞인다. **최종 리뷰 dispatch에 이 항목을 명시적으로 실을 것.**

**Task 16** — Minor 2건을 고친다 — (1) 조직 데이터 검사에만 vacuous-pass 방지 단언이 없다. **이건 내가 pre-flight에서 고친 바로 그 실패 모드다**(경로 버그로 0개 파일을 돌며 조용히 통과). 세 검사 중 유일하게 구조적 트립와이어가 없으므로 닫는다. (2) 색 리터럴 목록이 `.primary`/ `.secondary`/`Color(nsColor:)`/`Color(red:)`/`#colorLiteral`을 놓친다. 특히 `.primary`는 **테마를 인식하는 것처럼 보여서** 습관적으로 손이 가는데, 실제로는 이 앱의 팔레트가 아니라 시스템 팔레트를 따라가 테마 시스템을 우회한다
  · *틀렸을 경우 비용:* 없음. 현재 위반이 없어 즉시 통과했다. Minor 3(bare `atlassian.net` 미검출)은 실무에서 나올 수 없는 형태라 두기로 함.

**Task 16** — 조직 데이터 검사를 금지목록 → 허용목록으로 뒤집는다 (계획 수정, 833d676) — 계획 원문의 `let forbidden = ["flyingdoctor", ...]`는 그 테스트 파일 자체가 조직명을 리포지토리에 남긴다. 사용자가 "flyingdoctor 사내 Jira 민감정보를 git history까지 모두 제거"를 요구했으므로 정면 충돌이다. `example.atlassian.net` 외의 Jira 호스트가 보이면 실패하는 정규식으로 바꿨고, 검사 범위에 Tests도 넣었다(제약 문구가 "코드나 테스트에"이다)
  · *틀렸을 경우 비용:* 정규식이 `atlassian.net` 호스트만 보므로 프로젝트 키(예: 실제 프로젝트 접두사) 유출은 못 잡는다. 그건 리뷰어의 눈과 이 계획의 다른 제약이 계속 담당한다.

**Task 16** — `sourcesDirectory()`의 경로 버그를 고친다 (같은 커밋) — `#filePath`에서 두 번만 상위로 올라가 `Tests/Sources`를 가리켰다. 패키지 루트까지 세 번 올라가도록 `packageRoot()`로 분리했다. 주석은 원래도 세 단계를 의도하고 있었다
  · *틀렸을 경우 비용:* 없음(Task 16 실행 시 `#expect(!files.isEmpty)`가 즉시 잡았을 버그를 미리 없앤 것).

## 미결 사항

### 시각 확인 (2026-08-14, 화면 잠금 해제 후 부분 수행)

로그인 화면을 실제로 띄워 확인했다. 확인된 것:

- 입력란 3개 · "API 토큰 발급받기" 링크 · "연결" 버튼이 모두 보인다
- 플레이스홀더가 `example.atlassian.net` / `you@example.com` — 조직 데이터 없음
- 폼이 720×512 창 중앙에 놓인다 (Task 11의 정렬 수정 반영됨)
- 다크 배경에 주황 타이틀, 대비 충분
- **`SecureField`가 접근성 트리에 토큰 값을 노출하지 않는다** (`value`가 빈 문자열)

**발견된 결함 (수정 완료, `733e20c`):** "연결" 버튼이 `enabled=false`인데 **파란 강조 배경으로
그려진다.** 글자만 흐릴 뿐 배경은 눌릴 것처럼 보인다. 원인은
`.keyboardShortcut(.defaultAction)` — macOS가 기본 버튼을 강조색으로 그리는데
`.disabled(true)`가 텍스트만 흐리게 하고 배경은 그대로 둔다. 첫 실행 사용자가
빈 폼에서 이 버튼을 누르고 아무 반응이 없는 것을 겪는다.
코드상 `.disabled(!canSubmit)`은 논리적으로 맞아 21번의 리뷰를 통과했고,
**렌더링 결과를 봐야만 드러나는 종류의 결함이다.**

수정: `canSubmit`일 때만 `.defaultAction` 지위를 준다. 확인 결과 빈 폼에서는
어두운 회색 배경 + 흐린 글자, 채워진 폼에서는 밝은 파란 배경으로 명확히 갈린다.

**같은 세션에서 Task 11의 핵심 수정도 실물로 검증했다**: 잘못된 자격증명으로
로그인을 시도하자 "이메일 또는 토큰이 올바르지 않습니다."가 빨간색으로 뜨고
**세 입력값이 모두 그대로 남았다**. 수정 전이었다면 SwiftUI가 뷰를 재생성해
전부 비워졌을 것이다. 에러 문구에 사이트·이메일·토큰이 들어있지 않은 것도 확인.

### 아직 육안 확인되지 않은 화면

로그인 이후 화면들은 실제 Jira 자격증명이 있어야 볼 수 있어 아직 확인되지 않았다:

- 매핑 마법사 (상태 목록·드롭다운·미매핑 안내·시작하기)
- 관측 캐비닛 (카드·상세 시트·빈 상태)
- 아케이드 플로어 (마퀴·캐비닛 3칸·상태바·새로고침)
- 에러 표시 (expired 배너·연결 실패·경고 배너 두 종의 구분)

특히 눈으로 봐야 하는 지점: 로그인 화면과 매핑 마법사의 정렬 일관성,
`RootView`의 `minWidth: 720/minHeight: 480`과 `windowResizability(.contentSize)` 조합,
`SignInView`의 이중 frame(`maxWidth: 480` 후 `maxWidth: .infinity`).

Task 10에서 라이트/다크 전환은 실제로 확인됐다(다크 ~#0a0a0f + 주황, 라이트 크림 + 갈색).
