# 퀘스트 보드 시각 검증 체크리스트

이 체크리스트는 테스트로 검증할 수 없는 UI 동작을 수동으로 확인하는 절차입니다. **한 번의 앱 실행으로 모두 확인 가능하도록 구성했습니다.**

---

## 준비

```bash
cd Packages/Jirarcade
swift run JirarcadeApp
```

앱이 띄워지고 로그인 → 워크플로 매핑 → 아케이드 플로어까지 진행합니다.

## 1. 아케이드 플로어 구성 (Task 8)

### 1.1 캐비닛 목록 확인
- [ ] QUEST BOARD 카드가 보인다
- [ ] OBSERVATION 카드가 보인다  
- [ ] 세 번째 슬롯에 "coming soon" 플레이스홀더 하나만 있다 (중복 없음)

### 1.2 퀘스트 보드 전체 화면 전환
- [ ] QUEST BOARD의 "▶ OPEN" 버튼을 누른다
- [ ] 보드가 전체 화면으로 띄워진다 (플로어 배치는 사라짐)
- [ ] 상단에 "◂ FLOOR" 버튼과 제목이 있다
- [ ] 제목 아래 구분선이 있다
- [ ] "◂ FLOOR" 버튼을 누른다
- [ ] 플로어로 돌아간다
- [ ] 전체 화면 상태에서 Esc를 누른다
- [ ] 플로어로 돌아간다

### 1.3 OBSERVATION 카드 (기존 동작, 시트 방식)
- [ ] OBSERVATION의 "▶ OPEN" 버튼을 누른다
- [ ] 관측 상세가 시트로 띄워진다 (플로어 배치는 남아 있음)

## 2. 보드 축과 레인 렌더링 (Task 9)

이 항목은 QUEST BOARD 전체 화면이 띄워진 상태에서 확인합니다.

### 2.1 축 범위와 눈금
- [ ] 보드의 좌측에 시간축이 그려진다
- [ ] 축에 일차 레이블 (예: 0d, 7d, 14d 등)이 있다
- [ ] 각 레이블의 위치가 균등하게 분포한다

### 2.2 상태별 레인
- [ ] 보드가 상태 레인들로 나뉜다 (BACKLOG, ACTIVE, REVIEW, VERIFY)
- [ ] 각 레인의 헤더에 상태명이 쓰여 있다
- [ ] 헤더 오른쪽에 티켓 개수가 표시된다 (예: "4")

### 2.3 카드 배치
- [ ] 각 카드가 정체일에 따라 축 위에 배치된다
- [ ] 같은 레인에서 두 개 이상의 카드는 겹치지 않는다 (필요하면 아래로 쌓인다)
- [ ] 카드의 좌측 가장자리가 축의 시작점(0d)에 가깝고, 우측이 축의 끝에 가깝다

### 2.4 윈도우 크기 조정 시 카드 배치
- [ ] 앱 윈도우를 매우 좁게 줄인다 (예: 300pt 정도)
- [ ] 카드들이 여전히 겹치지 않고 수직으로 쌓인다
- [ ] 가독성이 손상되지 않는다

### 2.5 빈 레인
- [ ] 티켓이 없는 레인이 있는 경우, 그 레인도 축 선과 눈금이 보인다
- [ ] "여기에 아무것도 없다" 같은 메시지나 상태가 시각적으로 명확하다

## 3. 보드 HUD (Task 10)

QUEST BOARD 전체 화면의 최상단을 확인합니다.

### 3.1 시즌 요약 섹션
- [ ] HUD 행의 좌측에 시즌 정보가 표시된다
- [ ] 레벨 숫자가 보인다
- [ ] XP 진행률 바가 보인다
- [ ] 연속 일수 카운터가 보인다

### 3.2 위생 섹션
- [ ] HUD 행의 우측에 위생 정보가 표시된다
- [ ] HP 아이콘 (하트)이 최대 3개까지 보인다
- [ ] HP 점수 (0~3의 숫자)가 표시된다
- [ ] 위생 스코어 (50~100 범위 숫자)가 표시된다
- [ ] "다음 개선" 항목이 있으면 그 텍스트가 보인다

### 3.3 첫 동기화 전
- [ ] 앱을 처음 실행하고 아직 동기화하지 않았다면, HUD가 비어 있거나 최소한 데이터를 표시하지 않는다

### 3.4 동기화 후
- [ ] 동기화가 끝나면 HUD에 실제 데이터가 표시된다

## 4. 상태 전이 메뉴와 카드 애니메이션 (Task 11)

**중요: 이 섹션은 특별히 주의해서 검증하세요. 다음 항목 4.1과 4.2는 구현 위험이 존재합니다.**

### 4.1 ✓ **전이 메뉴는 매번 새로 불러와야 함 (캐싱 금지)**

**목표**: 메뉴가 열릴 때마다 Jira 워크플로 후보를 새로 가져온다는 것을 확인.

**과정**:
1. 카드 하나를 선택하고 "상태 옮기기" 메뉴를 연다
2. 로딩 상태 ("불러오는 중…") 또는 후보 목록이 표시되는 것을 본다
3. 메뉴를 닫는다 (Esc 또는 다른 곳 클릭)
4. **같은 카드의 메뉴를 다시 연다**
5. 로딩 상태가 **다시 나타나는지 확인한다**

**기대**: 로딩 상태가 두 번째 열때도 나타난다 (캐시되지 않음).

**만약 안 된다면**: 
- 메뉴가 처음 열 때만 로딩되고 두 번째에는 즉시 목록이 보인다면 캐싱 문제가 있다
- 이 경우 admin이 Jira 워크플로를 변경했을 때 앱이 잘못된 상태로 전이를 시도할 수 있다

### 4.2 ✓ **카드 높이와 실패 메시지 표시 (클리핑 금지)**

**목표**: 카드의 높이가 충분해서 전이 실패 시 모든 정보를 볼 수 있다.

**과정**:
1. 마감일 라벨이 있는 카드를 찾는다
2. 해당 카드의 "상태 옮기기" 메뉴에서 다음 상태를 선택해 전이를 요청한다
3. 또는 전이가 실패하도록 유도한다 (admin이 워크플로를 변경하거나 다른 방법)
4. 카드에 실패 메시지가 표시된다
5. **마감일 라벨이 사라지고 그 자리에 실패 메시지가 나타난다** (마감일과 실패는 동시에 보이지 않음)
6. 실패 메시지 전체, "Jira에서 열기" 링크, "닫기" 버튼이 모두 **카드 아래쪽이 잘리지 않고** 한 줄에 보인다
7. **"닫기" 버튼을 누르면** 실패 블록이 사라지고 마감일 라벨과 "상태 옮기기" 메뉴가 다시 나타난다 (또는 다른 전이를 시도해도 같은 결과)

**기대**: 실패 메시지 블록의 모든 줄(실패 이유 + "Jira에서 열기"·"닫기" 행)이 완전히 보인다. 높이 112pt는 이를 위해 조정됨. "닫기"는 `jiraURL`이 없을 때(사이트 호스트를 아직 못 받았을 때)도 항상 보여야 한다 — 그렇지 않으면 실패한 카드가 세션 내내 메뉴를 다시 열 방법이 없다.

**만약 안 된다면**: 
- 실패 메시지나 "Jira에서 열기" 링크가 카드 아래에서 잘린다면, 사용자가 왜 전이가 실패했는지 알 수 없고 Jira에서 추가 정보를 찾을 수 없게 됨.
- "닫기" 버튼이 없거나 눌러도 실패 블록이 사라지지 않는다면, 그 카드는 실패가 뜬 순간부터 세션이 끝날 때까지 "상태 옮기기" 메뉴로 돌아갈 방법이 없어 다른 전이를 시도할 수 없게 됨.

## 5. 카드 상태 전이 동작 (Task 11)

### 5.1 낙관적 이동과 애니메이션
- [ ] 카드의 "상태 옮기기" 메뉴를 열고 다음 상태를 선택한다
- [ ] 카드가 **즉시** 새 상태 레인으로 이동한다 (로딩 대기 없음)
- [ ] 카드의 이동이 부드러운 스프링 애니메이션으로 보인다

### 5.2 5초 카운트다운 취소 윈도우
- [ ] 전이 후 카드에 "취소" 버튼이 있는 pending 배너가 표시된다
- [ ] 배너에 대상 상태가 쓰여 있다
- [ ] 배너에 **남은 시간이 초 단위로("5s" 형태) 표시되고 매초 줄어든다** — 5 → 4 → 3 → …
- [ ] 카운트다운이 줄어드는 동안 카드의 다른 줄(요약·마감일 등)은 다시 그려지지 않는다(깜빡임 없음)
- [ ] "취소" 버튼을 누른다
- [ ] 카드가 **원래 레인으로 돌아온다** (애니메이션됨)
- [ ] Jira 웹에서 보면 상태가 변경되지 않았다 (앱이 실제 요청을 보내지 않음)

### 5.3 5초 후 자동 전이
- [ ] 다시 카드에서 "상태 옮기기" → 상태를 선택한다
- [ ] Pending 배너가 표시되고 **5초 동안 기다린다** (시계로 확인)
- [ ] 5초가 지나면 배너가 사라진다
- [ ] Jira 웹에서 확인하면 상태가 실제로 변경되었다
- [ ] 앱을 다시 동기화하면 카드에 XP가 붙는다

### 5.4 Reduce Motion 설정
- [ ] macOS 시스템 설정 > 손쉬운 사용 > 디스플레이 > 동작 줄이기 를 켠다
- [ ] 앱으로 돌아간다
- [ ] 카드에서 "상태 옮기기" → 상태 선택
- [ ] 카드가 **애니메이션 없이 즉시** 새 레인으로 옮겨진다 (스프링 효과 없음)
- [ ] "취소"를 눌러 원래 상태로 돌아올 때도 즉시 옮겨진다 (애니메이션 없음)

## 6. 매핑되지 않은 티켓 레인 (Task 12)

### 6.1 매핑된 상태와 미매핑된 상태
- [ ] 일부 티켓의 상태가 **워크플로 매핑 시 연결되지 않았다** (또는 테스트용으로 특정 상태를 매핑 해제한다)
- [ ] 그러한 티켓들이 보드에 **사라지지 않고** 별도의 "매핑되지 않은 티켓" 레인에 표시된다

### 6.2 미매핑 레인 기본 상태 (접혀 있음)
- [ ] 보드 최하단에 "매핑되지 않은 티켓" 섹션이 보인다
- [ ] 섹션이 **기본적으로 접혀 있다** (화살표 또는 expand 표시)
- [ ] 티켓 개수가 "N건" 형태로 표시된다

### 6.3 미매핑 레인 펼치기
- [ ] "매핑되지 않은 티켓" 섹션의 헤더를 클릭하거나 expand 버튼을 누른다
- [ ] 미매핑 상태의 모든 티켓이 목록으로 표시된다
- [ ] 각 티켓에 key, 상태명(미매핑 상태), 요약이 표시된다

### 6.4 매핑 고치기
- [ ] 미매핑 레인에 "매핑 고치기" 버튼이 있다
- [ ] 버튼을 누른다
- [ ] 워크플로 매핑 마법사 화면이 띄워진다
- [ ] 매핑을 변경하고 완료한다
- [ ] 다시 퀘스트 보드로 돌아온다
- [ ] 미매핑 레인의 티켓들이 사라지고 적절한 상태 레인에 표시된다 (또는 티켓 개수가 줄어든다)

## 7. 빈 상태 (Task 12)

### 7.1 동기화 전 (처음 실행, 또는 데이터 삭제 후)
- [ ] 동기화를 아직 하지 않은 상태에서 퀘스트 보드를 연다
- [ ] "아직 동기화하지 않았습니다"라는 메시지가 보인다
- [ ] 추가 안내문 (예: "첫 동기화가 끝나면 내 티켓을 보여줄게요")이 있으면 함께 표시된다

### 7.2 동기화 후, 담당 미완료 티켓 없음
- [ ] 동기화가 완료되었지만, 사용자가 담당한 미완료 티켓이 정말로 없는 상태를 만든다
  (또는 테스트 계정이 그런 상태라면 그대로 확인)
- [ ] 보드가 비어 있고 "담당한 미완료 티켓이 없습니다"라는 메시지가 보인다
- [ ] 추가 안내문 (예: "Jira에서 티켓을 맡으면 여기에 나타나요")이 있으면 함께 표시된다

### 7.3 매핑되지 않은 티켓만 있는 경우
- [ ] 사용자가 담당한 **모든** 미완료 티켓의 상태가 매핑되지 않은 경우
- [ ] 메인 레인은 비어 있고 (빈 상태 메시지 표시)
- [ ] **"매핑되지 않은 티켓" 레인은 여전히 보인다** (경계 예시: 사용자가 매핑 없이도 이 티켓들을 관리할 수 있음)

## 9. 오프라인 동작 (Spec §7.4, v0.1 완성 정의)

### 9.1 네트워크 끊은 상태에서 앱 재실행
- [ ] Wi-Fi를 끈다 (또는 네트워크를 비활성화한다)
- [ ] 앱을 완전히 종료한다
- [ ] 앱을 다시 실행한다
- [ ] 앱이 정상적으로 띄워진다 (충돌하지 않음)
- [ ] 퀘스트 보드가 **마지막으로 동기화된 데이터로 그려진다**

### 9.2 오프라인 상태에서 전이 시도
- [ ] 여전히 Wi-Fi가 끈 상태에서 유지한다
- [ ] 퀘스트 보드의 카드에서 "상태 옮기기" 메뉴를 누른다
- [ ] 메뉴의 후보 목록이 **비어 있다** (또는 "불러올 수 없음" 같은 상태)
- [ ] 앱이 **멈추거나 충돌하지 않는다** (graceful 하게 처리함)

## 10. 스펙 §11 완성 정의 체크리스트

(이 항목은 위의 섹션들을 집계한 것입니다. 위 항목들을 모두 확인하면 이 체크리스트도 자동으로 완료됩니다.)

- [ ] 플로어에서 QUEST BOARD를 열면 내 미완료 티켓이 단계별 레인에 전량 뜬다
- [ ] 티켓이 정체일에 따라 축 위에 놓이고, 눈금이 RuleSet의 경계값과 일치한다
- ☑️ 규칙 JSON에서 bossDays를 바꾸면 축 눈금과 등급이 함께 움직인다 **(자동 테스트로 보장: `BoardAxisTests.ticksFollowACustomRuleSet`)**
- [ ] 관측 이력이 없는 티켓의 정체일에 근사 표시(~)가 붙는다
- [ ] 매핑되지 않은 상태의 티켓이 보드에서 사라지지 않는다
- [ ] 카드에서 상태를 옮기면 5초 안에 취소할 수 있고, 취소하면 Jira에 아무 일도 없다
- [ ] 5초가 지나 전이가 성공하면 Jira 웹에서 확인되고, 다음 동기화에서 XP가 붙는다

### 실계정 전이 테스트 (MPT-9563, 2026-08-24)

`--restore-window`를 붙이면 메뉴 팝업도 접근성 트리에 잡힌다(첫 시도에서 실패한 것은 그
플래그가 없었기 때문이다). 실제로 전이를 두 번 실행해 Jira 반영까지 확인했다.

| 항목 | 결과 |
|---|---|
| §5.1 낙관적 이동 | 확인 — 카드에 `→ STAG 반영` / `→ 진행 중` 대기 배너 |
| §5.2 5초 내 취소 | 확인 — 사용자가 직접 검수 |
| §5.3 5초 후 자동 전이 | 확인 — 11:38 `진행 중 → STAG 반영`, 11:42 원복. 둘 다 Jira API로 반영 확인 |
| §4.1 메뉴 재요청 | 부분 확인 — `.onAppear`가 발화하고 후보 17건을 실제로 받아온다(1회차 "불러오는 중…" → 2회차 목록). **"매 열기마다"인지는 미확정** — 메뉴가 클릭마다 토글되고 `get-app-state`가 메뉴를 닫아, 관찰 창이 클릭 응답 스냅샷 하나뿐이다 |

**이 테스트가 실제 결함을 하나 잡았다.** 메뉴에서 "검토 중"을 골랐는데 티켓이 "STAG 반영"으로
갔다. `JiraTransition`의 전이 이름(`name`)과 도착 상태(`toStatusName`)가 다른 워크플로였고,
메뉴가 이름만 보여주고 있었다. 자동 테스트의 픽스처는 늘 둘이 대응하는 데이터였기 때문에
실데이터에서만 드러났다 — 시각 확인이 존재하는 이유다.
고친 뒤로 메뉴는 둘이 다를 때 `검토 중 → STAG 반영`처럼 함께 보여준다
(`JiraTransition.menuLabel`, `TransitionLabelTests`가 고정).
### 도구 한계로 확인 불가

- **§2.4 좁은 창 배치** — `capabilities`의 `windows.moveResize: false`. 창 크기를 바꿀 수 없다.
- **스크린샷 전반** — `get-app-state`가 `screenshot` 필드를 돌려주지 않았다.

### 조건이 없어 확인 불가

- **§6 미매핑 티켓 레인** — 현재 계정의 모든 상태가 매핑돼 있어 미매핑 티켓이 0건이다.
  레인이 뜨지 않는 것이 정상 동작이며, 레인 자체는 미매핑 상태가 생겨야 볼 수 있다.
- **§2.5 빈 레인** — 네 레인 모두 티켓이 있다.

### 자동 확인 시 알아둘 것

`swift run JirarcadeApp`으로 띄운 프로세스는 **접근성 API에 창이 보이지 않는다**
(`window_not_found`). 번들 없이 실행하면 백그라운드 전용 앱으로 등록되기 때문이며,
앱이 활성화 정책을 `.regular`로 올려도 접근성 쪽에서는 잡히지 않았다.
`./scripts/make-app.sh --open`으로 번들을 만들면 `dev.jirarcade.app` 번들 ID를 갖고 정상 동작한다.
**UI 자동 검증은 번들로 띄워야 한다.**
