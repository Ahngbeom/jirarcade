브랜치 `Ahngbeom/chore-release-ci` · 6개 태스크 · 리허설 태그 `v0.0.1-rc.1`
(run `32467875898`, run number 1) · 최종 439 tests

이 문서는 리허설이 실제로 증명한 것, 리뷰가 정적 분석만으로는 못 잡았을 결함,

문서가 지금 모양인지에 대한 답이 여기 있다.

## 리뷰가 정적 분석만으로는 못 잡았을 결함

Task 4 리뷰(구현자가 짠 `release.yml` 초안에 대한)가 잡아낸 6건의 Minor 중
지금 고치지 않았으면 리허설이 깨진 채로 통과했을 두 건.

**릴리즈를 먼저 공개하고 나중에 자산을 올리던 순서.** `gh release create`는
기본적으로 릴리즈를 즉시 공개한 뒤 자산을 업로드한다. 50MB 안팎의 zip 업로드가
중간에 끊기면, 다운로드할 게 없는 릴리즈가 이미 공개된 채로 남는다. 정적으로
읽으면 "릴리즈 만들고 zip 붙인다"로 보여 문제가 없어 보이지만, 실패 모드는
네트워크 타이밍에 달려 있어 코드만 봐서는 드러나지 않는다. `--draft`로 만들고
업로드가 끝난 뒤 `--draft=false`로 뒤집는 순서로 고쳤다 — 이번 리허설의
`릴리즈 생성` 스텝 로그가 실제로 그 순서(`untagged-<hash>` 초안 URL → 태그
URL)로 실행됐음을 보여준다.

**Xcode 고정이 성공했는지 단언하지 않던 것.** 원래 코드는 `xcode-select -s`를
실행하고 `swift --version`을 찍기만 했다. 경로가 있으면 `xcode-select`는
성공하지만, 그 경로 안의 Xcode가 실제로 26.2라는 보장은 없다 — 러너 이미지가
같은 경로에 다른 버전을 심어도 이 스텝은 통과한다. `xcodebuild -version`의
결과를 `26.2`와 비교해 다르면 즉시 실패하도록 단언을 추가했다. 아래 드리프트
항목이 이 단언이 왜 장식이 아닌지를 보여준다.

## 툴체인 드리프트 — 설계가 의도대로 작동했다

스펙 §4.3은 검증 CI와 릴리즈 CD가 툴체인에 대해 반대 방향을 선택하게 설계했다 —
CI는 러너의 기본 Xcode를 그대로 쓰고 `swift --version`만 로그로 남겨 "미래에
깨지는가"를 지켜보고, 릴리즈는 `xcode-select -s`로 26.2를 명시적으로 고정해
"어제와 같은가"를 보장한다.

이 자산은 첫 CI 실행에서 바로 값을 냈다. Task 3에서 러너를 실측하니 **기본
(비고정) 툴체인이 이미 Xcode 26.6 / Swift 6.3.3**이었다 — 이 프로젝트의 개발
환경(Swift 6.2.3 / Xcode 26.2)과 어긋난 지 오래다. `macos-26` 이미지가 GA
상태에서도 조용히 상향된 것이다. CI가 이 드리프트를 가정이 아니라 실측으로
먼저 만났고, 릴리즈 워크플로는 여전히 26.2를 명시적으로 골라(`/Applications/Xcode_26.2.app`)
고정하므로 영향받지 않았다 — 비대칭 설계가 가상의 시나리오가 아니라 이번
브랜치 작업 중 실제로 일어난 일을 잡아냈다.

이 발견은 스펙 §4.3의 문장도 정정하게 만들었다 — "기본 Xcode가 26.2이고 개발
환경과 일치한다"는 더 이상 사실이 아니라, 실측값(26.6/6.3.3)으로 고쳤다(이
커밋). 설계 결정(CI 비고정·릴리즈 고정) 자체는 바뀌지 않는다 — 오히려 이번
드리프트가 그 결정이 옳았다는 증거다.

## 측정값이 두 번 틀렸다가 바로잡힌 경우들

README의 낡은 "221개" 테스트 수가 이 계획의 출발점이었다. 같은 실수를 반복하지
않으려고 두 숫자 모두 계획의 상수를 베끼지 않고 직접 측정하게 지시했는데, 그중
하나는 측정 자체가 한 번 더 틀렸다.

**테스트 개수.** 계획 문서의 상수 `439`를 그대로 옮기지 않고 구현자가 직접
`swift test`를 돌려 측정했다 — 결과가 우연히 계획과 같은 439였지만, 옮겨적은
게 아니라 독립적으로 재확인한 값이다. (참고: PR 병합 참조 기준으로는 441이
나온다 — 이 브랜치가 `origin/main`보다 2커밋 뒤처져 있기 때문이며, 병합
시점에 다시 측정해야 하는 별개의 숫자다.)

**소요 시간은 두 번 틀렸다.** 계획은 "0.8초"라고 적어뒀다. 구현자가 실측한
wall clock(`swift test` 전체 실행 시간)은 2.0~2.7초였고, 이를 반영해 README에
"3초 안에"라고 썼다. 그런데 재실행이 즉시 이 문장을 반증했다 — wall clock을
다시 재니 3.34초가 나와 "3초 안에"가 깨졌다. wall clock은 컴파일·링크 시간에
좌우돼 재실행마다 흔들리는 지표였던 것이다.

바로잡은 값은 프레임워크가 스스로 보고하는 테스트 실행 시간(`swift test`가
찍는 `"Test run with 439 tests in 0 suites passed after N seconds"` 줄, 빌드·링크
시간 제외)이다. 세 번 관측한 값이 0.803초·1.082초·1.338초였고, 이 셋을 모두
만족하는 상한으로 README에 "2초 안에"라고 적었다.

프레임워크가 보고하는 시간이 맞는 지표인 이유: 원래 문장("221개 테스트가 약
0.2초에 끝납니다")이 처음부터 재던 것이 바로 이 값이다. 빌드 단계를 포함하는
`swift test` 호출이 0.2초에 끝나는 일은 있을 수 없으므로, 그 문장은 애초에
빌드 시스템의 처리량이 아니라 테스트 스위트 자체의 속도를 말하고 있었다.
문장의 주어가 원래 그것이었으니, 정정도 같은 지표로 하는 것이 문장의 원래
의도에 맞다.

## 아직 검증되지 않은 것

**Intel 실행.** `lipo -archs`가 `x86_64 arm64`를 보여줘 슬라이스가 "들어있다"는
사실은 확인했다. 그러나 이 리허설은 arm64 맥에서 실행됐고, x86_64 바이너리를
실제 Intel 맥(또는 Rosetta)에서 켜본 적은 없다. 스펙 §10 리스크 1이 그대로
남는다 — 수령자 중 Intel 사용자의 첫 실행이 유일한 확인이 될 것이다.

**정확한 시스템 대화상자 문구.** README와 릴리즈 노트가 인용하는
"손상되었기 때문에 열 수 없습니다"는 GUI 대화상자를 실제로 띄워야만 확인된다.
대신 확인한 것: 격리 속성(`com.apple.quarantine`)이 붙은 상태에서
`spctl --assess --type execute`가 `rejected`를 냈고, README가 안내하는
`xattr -d com.apple.quarantine` 실행 후 그 속성이 사라졌으며 그 뒤에도
`codesign --verify --deep --strict`가 통과했다. 안내의 전제(차단됨)와 처방(이
명령이 푼다)은 둘 다 사실로 확인됐지만, 정확한 문구 자체는 확인하지 못한 채로
남긴다 — 확인됐다고 적지 않는다.

**⌘V 붙여넣기.** 다운로드한 앱을 실행하니 이미 로그인된 상태로 떴다 — 같은
번들 ID(`dev.jirarcade.app`)를 쓰는, 이 개발 머신에서 동시에 돌고 있던
무관한 세션의 Jirarcade 프로세스가 남긴 Keychain/앱 지원 데이터를 물려받은
것이다. 그래서 자격증명 입력 화면 자체가 나타나지 않았고, 포커스를 받을 수
있는 편집 가능한 텍스트 필드에 접근하지 못했다. Edit 메뉴는 존재를 확인했고
(`Cut·Copy·Paste·...`), 아무 필드에도 포커스가 없는 상태에서 `Paste`가
정확히 비활성(disabled)이었다는 것까지는 확인했다 — 이는 메뉴가 죽은 게
아니라 포커스 상태에 반응한다는 증거다. 그러나 실제로 텍스트 필드에 포커스를
주고 ⌘V가 값을 넣는 것 자체는 확인하지 못했다.

## 다음 사람이 첫 정식 릴리즈를 낼 때

1. `git tag vX.Y.Z && git push origin vX.Y.Z` — 하이픈이 없으면 "최신 릴리즈"
   자리를 차지하므로 진짜 준비된 버전에서만 민다.
2. `gh run watch --exit-status`로 지켜보고, `출하 전 검증`의 다섯 줄 `✓`와
   Xcode 고정 스텝의 성공을 확인한다.
3. `gh release view vX.Y.Z`로 본문·자산·prerelease 여부를 확인한 뒤, 실제로
   다운로드해 `lipo`/`plutil`/`codesign`을 돌리고 앱을 한 번 띄워 수령자
   입장에서 끝까지 밟아본다 — 초록 워크플로가 곧 올바른 산출물이라는 뜻은
   아니다.
4. `gh release create`는 성공했는데 뒤이은 `gh release edit --draft=false`가
   실패하면, 자산은 올라갔지만 릴리즈가 draft로 남는다. 같은 태그를 그냥 다시
   밀면 기존 draft와 충돌한다 — `gh release view vX.Y.Z`로 draft 여부를 먼저
   확인하고, `gh release edit vX.Y.Z --draft=false`로 수동 공개하거나
   `gh release delete vX.Y.Z --yes`로 draft를 지운 뒤에 태그를 다시 민다.
